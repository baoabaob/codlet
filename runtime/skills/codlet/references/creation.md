# 创建或修改 Codlet 插件

先沿用用户已明确提供的信息；只询问缺少的项目，可合并相关选择，避免重复确认。

1. 需求不清楚时，先澄清触发时机、预期行为、界面或输入输出，不擅自扩大功能
2. 未给名字时，按功能建议几个易懂的名字，让用户选定或输入自己的名字；确认后再合理生成技术 ID
3. 未给目录时，展示 `runtime.json.defaultPluginsDirectory` 下建议的插件子目录，询问默认目录还是自定义位置。不要覆盖已有文件，不修改 Core 管理的 `packages/github/` 安装包
4. 未说明 UI 选择时，询问是否使用官方 UI 组件和样式，默认不使用。此时只解释是否希望与客户端一致；用户选用后才读 [官方 UI 参考](official-ui.md)，不要提前展开组件清单。不使用官方 UI 不排除其他适配层依赖
5. 功能大致敲定后，用 scoped CLI 的 `plugin list --json` 检查实际已安装插件及 manifest 的 provides/requires。列出可依赖的插件、推荐理由和“也可以不依赖”。需要客户端集成时优先推荐 Codlet 提供的 `codex.desktop.adapter`、`codex.ui.adapter` 等适配层中确实存在的能力；不要为零依赖重新猜私有接口。没有适合的能力时说明原因，允许独立实现。等待用户确定依赖选择
6. 实现前，用简单语言说明代码在哪运行（界面、后台或两者）、必要权限及其能读写的内容和影响范围，让用户确认。已有明确授权时不重复问，不能顺手请求全部权限

创建阶段先按当前运行实例的平台与客户端语言完成可用版本，不提前展开发布平台、i18n 和仓库问卷。用户已明确的跨平台、多语言或发布需求照常执行；缺失信息若会阻碍当前功能，仍及时澄清，不能为了延后发布问询而忽略当前使用要求。

确认后读 [开发契约](plugin-api.md)，仅按实际层级加载类型和详细文档。需求是修复已有插件时保留已确定的选择，不重新做问卷。

- 使用 `codlet.json` 和构建好的 CommonJS 入口；TS 先构建，Core 不执行 npm 安装或即时编译
- 前端私有接口/节点依赖必须检查当前客户端源码和真实结构，不凭截图或模糊文字猜；验证普通消息和其他功能不受影响
- 检查平台边界：纯 Adapter 调用也要以所需能力和依赖链的平台交集为准。原生模块、系统命令、专有路径/文件格式、平台分支、私有客户端接口或未覆盖的第三方依赖需要显式兼容声明；静态扫描没有发现问题只是线索，不是全平台验证。声明支持、推导范围与实际验收记录分开保存
- 实现停用清理：移除自己的节点/样式，断开 observer、监听、定时器，取消请求，重载不重复注册
- 验证实际功能；有 UI 就验收浅/深色和合理窗口宽度，多语言还要检查切换、回退和文字溢出。未做的设备验收在开发记录中明确记录，不把假设写成已通过的测试
- 使用 [管理 CLI](management.md) 预览并按已确认权限注册。默认目录不表示可以覆盖现有同 ID 插件；注册冲突先检查现有来源
- 用户已经要求安装并启用时直接完成。额外上传到 GitHub、发布或扩大权限需要对应授权
- 最后简述名称、目录、用法、验证和限制

## 完成后再决定是否发布

本地创建与必要验证完成后，询问是否需要发布。用户只想自用则到此结束，不要求填写发布资料；用户已经要求发布时不重复询问这个决定。

选择发布后，再合并询问尚未明确的信息：

- 目标平台：Windows、macOS 还是两者，是否有架构限制。推荐沿用所需 Adapter/Core 能力的共同支持范围；超出适配层或包含系统相关代码时需要明确的平台声明
- 语言范围：是否跟随客户端语言，支持哪些语言（可推荐中文和英文），还是保持单一语言。官方 UI 组件不自动提供插件文案的 i18n；多语言需覆盖名称、说明、菜单、设置、状态和错误文案，并有翻译回退。技术 ID、权限名和标签不翻译
- 发布目标与资料：仓库、可见性、版本、作者和说明，以及安装依赖、许可与必要的使用文档；先沿用已有信息，不逐项重复确认

随后补齐已确定范围的实现、测试、包元数据和安装包。准备可审阅的发布结果，按用户已授权的仓库和可见性执行；没有获得公开发布授权时，不把本地可用或同意私有上传解释成允许公开。支持声明与真实平台验收记录分开，不补写未执行的测试。
