# Codlet 与官方插件性能分析 · 2026-09-21

本轮发现并修复了两处不必要的全页扫描。受测的 Core 渲染器运行时、Desktop Adapter、UI Adapter 和 GUI 未表现出随启停代数或消息数持续累积大量内存的现象。这是限定工作负载的结果，不能据此保证长时间运行绝无泄漏。

**原生 Core 进程常驻内存的真实客户端测试未完成。** 新编译的隔离测试运行器被 Windows Defender 隔离；本报告不会用 Node 堆代替该指标。源码优化已构建、通过相关回归；没有替换用户安装的 Preview 4，也没有生成新安装包。

## 测试条件与口径

- Windows 11 x64，Build 26200；i7-12700K，20 个逻辑处理器，约 32 GB 内存。
- 优化前源码：Core `c4b1c22`；官方插件 `c5ecacd`。三个插件为 Desktop Adapter 0.1.0、UI Adapter 0.1.1、GUI 0.1.1。
- 扫描前后对比均使用 Node v24.18.1、生产构建、jsdom，工作负载和预热相同；CSS 解析被禁用。该对比测的是 JS/DOM 处理成本，**没有测量 Chromium 绘制、模型服务或实际网络吞吐**。
- Core 渲染器和最终 GUI 压测使用分发固定的 Node v24.21.0。所有生命周期堆采样前完成事件循环轮转和三次显式 GC；统计的是预热后的保留 JS 堆变化。
- Desktop Adapter 使用模拟后端连接，成本不包含真实 React 服务定位、网络或原生 IPC。
- 私有内存是进程私有提交量；工作集是驻留页，跨进程相加会重复计算共享页；JS 堆又是另一种口径，三者不可互相替代。

对当前会话采样 62.8 秒、31 个点，固定跟踪 13 个客户端/后端进程，排除工具进程。采样时没有 Codlet Core 进程。此时会话仍在使用，不是严格空闲测试，也不是开启/关闭 Codlet 的同场 A/B。

| 指标 | 实测 |

## 已修复：聊天变化触发无关页面扫描

UI Adapter 在文档任何子节点变化后都会重新查询全页侧栏按钮；Core UI 的每个已注册页面也会重新查询挂载点。流式消息不断改写 DOM 时，未打开的 Codlet 页面仍承担这些工作。

现在只检查发生变化的子树。侧栏变化、页面挂载标记出现/消失、宿主或插件生命周期标记断开时才重新定位。Native 路由身份校验保留，并把同一操作中重复的两次 React 树定位合并为一次。没有采用延迟轮询，因此页面切换和卸载仍及时处理。

固定 1,000 个历史消息元素，顺序制造 1,000 次文本节点更新；预热 100 次，再测 5 轮，下面使用整段工作负载的耗时中位数：

| 组件 | 优化前 | 优化后 | 耗时减少 | 全页查询次数/轮 |
|---|---:|---:|---:|---:|
| 官方 UI Adapter | 151.79 ms | 25.38 ms | 83.3% | 1,000 → 0 |
| Core UI 页面挂载器 | 653.99 ms | 14.32 ms | 97.8% | 1,000 → 0 |

这不是“整台客户端快了 83%/98%”，也不是内存下降比例。实际收益取决于页面大小、消息变化频率和已注册插件页面数量。

## 内存与生命周期

| 组件 | 工作负载 | 用于比较的预热区间 | 回收后的 JS 堆增量 |
|---|---|---|---:|
| Core 渲染器运行时 | 200 轮启停、10,000 次 RPC | 第 10–200 轮 | +0.061 MiB |
| 官方 Desktop Adapter | 100 轮启停；另测 50,000 条消息 | 第 10–100 轮 | +0.003 MiB |
| 官方 UI Adapter | 60 轮注册和卸载页面 | 第 10–60 轮 | +0.182 MiB |
| Codlet GUI | 200 轮加载、打开、离开、卸载 | 第 100–200 轮 | +0.359 MiB |

各项均在独立 Node 进程内测量，不能相加成“Codlet 总内存”。GUI 和共享 UI SDK 的初次解析、React 初始化、jsdom/V8 缓存不包含在表中的稳定阶段增量内。

- Core：200 轮后插件状态为空，定时器和消息端口均为 0；额外空闲约 1 秒期间新增唤醒任务为 0。
- Desktop Adapter：50,000 条约 1 KiB 的消息，分成五批测量，缓存没有随累计消息数增长。实现同时限制事件数 256、序列化估算总量 1 MiB；它不是实际进程内存上限。停用后通知回调、测试模拟的 Core RPC 注册和清理钩子均为 0。
- UI Adapter：60 轮后自有导航节点为 0，观察器回到夹具初始数量。
- GUI：200 轮后自有页面/生命周期节点、媒体监听为 0；观察器和清理回调均回到夹具基线（各 1 个，来自共同的语言环境）。弱引用验证中，早期 199 代可回收，最后一代仍由采样时的 V8 调用栈引用。额外堆快照确认路径为 `GC roots → Stack roots → deactivate → Context → activate`，没有出现 200 代都被插件注册表保留的情况。这处单代栈引用不计为“全部对象已释放”。

结论是未复现大规模或按代累积的泄漏；没有证据把官方客户端的 GiB 级占用归因于本轮受测插件。长期驻留、大型真实会话、原生 Core 开销和第三方插件仍需另测。

## 验证与未完成项

通过相关检查共 68 项：Core UI 18 项、固定 Node 的空闲/RPC 4 项、两种 Adapter 43 项、GUI 导航/设置 3 项。前端构建、格式检查和 diff 检查通过。系统 Node 24.18.1 在额外 inspector 用例结束时发生 V8 崩溃，分发使用的固定 Node 24.21.0 下对应 4 项通过；该失败未被算入通过数量。

真实客户端尝试使用独立的既有实验配置，临时只启用三个官方插件。Windows Defender 报告 `Behavior:Win32/DefenseEvasion.A!ml` 并隔离新编译的 `codlet-lab.exe`，原生内存采样未开始，不能给出有效的常驻值或开启/关闭插件的进程差值。没有关闭防护、增加排除项或恢复被隔离的文件；已清理本次测试留下的 6 个客户端进程，并恢复原实验插件配置，保留原官方客户端会话。

后续应先分析该检测所对应的启动/注入行为，在获得正常可运行的测试路径后，再补充 release Core + 三插件的原生进程 A/B、至少 30 分钟驻留和实际长流消息测试。这是未完成的覆盖项，不能标记为已验收。

## 复测

Core 仓库：`node --expose-gc scripts/profile-renderer.mjs <输出.json>`。

官方插件仓库先执行 `node scripts/prepare-core-sdk.mjs <对应的 Core 绝对路径>`，再执行 `node --expose-gc scripts/profile-runtime.mjs <navigation|ui|desktop|gui> <输出.json>`。GUI 可设 `CODLET_PROFILE_CYCLES=200`；可选 `CODLET_PROFILE_HEAP` 指定本地堆快照路径。前后对比必须使用同一 Node 版本、相同测试参数和 SDK/插件构建。
