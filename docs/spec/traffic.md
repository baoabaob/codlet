# Traffic contract

This document is the stable contract for transparent traffic and the Host traffic API. It describes ownership and wire limits; client specific endpoint names stay in the official Adapter.

The process ingress uses generic plaintext sources. The Adapter's [request-chain verification](https://github.com/baoabaob/codlet-plugins/blob/main/docs/spec/request-chain.md) established separate Desktop JS and model-provider plaintext paths on a reviewed Windows build. Each source must be activated and report its own supported paths; this contract alone does not prove installed Desktop coverage.

## Ownership

Core owns one Rust traffic engine for transparent sources and explicit channels. It reuses the traffic authority's Tokio runtime; there is no permanent Node traffic worker or alternative JavaScript forwarding engine. The dispatcher uses an in-process authority peer, one authenticated loopback Host peer per plugin generation, and a separate private launch-source peer. Short service RPCs register policy and return status. Request bodies, response bodies and WebSocket frames use the bounded data peer only when a plugin consumes them. An unmatched request streams directly between native sockets. Renderer calls cannot create a peer or select an owner generation.

The Windows/macOS launch owner prepares the engine before client attachment and retains it until the owned client has retired. Core owns authority, private launch descriptors, and the selected launch plugin's bounded handshake; the ordinary authorized plugin owns client-specific hooks and routing. Core never depends on an official Adapter package. Plugin disable, revocation, generation replacement or peer failure retires affected registrations, sources, channels and exchanges. A request already sent upstream is never replayed after retirement. The short-lived Adapter launch executor and ordinary JavaScript plugin Hosts remain isolated from Core.

## Registration

Host code calls `context.traffic.registerInterceptor({ id, origins, priority?, timeoutMs? }, handlers)`. Origins are exact `http://` or `https://` origins with no path, credentials, query or fragment. Their `ws://` and `wss://` forms use the corresponding HTTP(S) origin grant. A registration is pending until its Host generation activates it on the data peer.

Core permits at most 32 registrations, 8 registrations per owner, 128 live interception leases, 512 pending data calls, 4 active intercepted HTTP exchanges and 32 active intercepted WebSocket exchanges. Explicit channel admission has its separate limits below. Registration metadata is at most 1024 bytes; handler timeout is 1–2000 ms. Priority is an integer from -1000 through 1000. Await `setEnabled(false)` to disable a registration and cancel its leases. `close()` and `dispose()` are equivalent asynchronous removals. `inspect()` is a synchronous local registration snapshot.

The dispatcher reads current registrations directly from the authority. Ordered change notifications acknowledge activation and source changes; there is no cached JavaScript registration snapshot. Origin grants, source access and lease operations retain their current-generation checks, and retirement notifications cancel live exchanges. A maximum of 32 LRU transport contexts reuse TLS/proxy configuration, partitioned by owner and exact trust/proxy credentials. This cache does not cache authorization or preserve a revoked profile; each forward resolves current permissions and profile/credential values before using it.

Request handlers run in ascending priority, plugin id and registration order. Response handlers run in reverse participation order. A handler may return one request rewrite, a synthetic response or a block. Redirects require `traffic.redirect` and a grant for the destination. Cross-origin rewrites carry only `Accept`, `Content-Type` and `Content-Encoding`. The transparent rewrite API does not accept `credentialRef`; the separate explicit channel forwarding API does.

Sensitive headers and WebSocket subprotocols are hidden unless the matching grant is declared and granted. The callback receives a frozen request view and an abort signal. Callback failures are reduced to finite public error codes; URLs, headers, credentials, body contents and callback error text are never written to diagnostics.

## Data limits and cancellation

Frames are length-prefixed JSON records no larger than 64 KiB. Each peer has at most 512 queued frames or 512 KiB queued bytes. Body sources have at most 8 live streams and 64 MiB per body; chunks are at most 32 KiB. WebSocket frames are at most 8 MiB. Reads, callback execution and leases have bounded deadlines. A cancelled, retired or expired lease rejects pending calls with `stream_retired` or `traffic_timeout` and sends no late result to a new generation.

HTTP parsing and framing use Hyper; HTTP(S) forwarding uses reqwest/rustls; WebSocket framing uses tungstenite. Native forwarding disables automatic retry, redirects, decompression and cookies. Repeated headers remain pairs and header values preserve Latin-1 wire bytes. CONNECT and unrecognized ingress upgrades are rejected before dispatch. WebSocket handshakes validate protocol selection before accepting the client; upstream 426/429 responses remain HTTP rejections. Each WebSocket direction pulls one message at a time with backpressure, so no unbounded callback queue is created. Existing queue/frame options remain accepted upper bounds; they do not require buffering that many messages.

Transparent routes preserve launch-time environment proxy/bypass settings and platform proxy resolution. Explicit channels use their declared network profiles. Inherited `NODE_EXTRA_CA_CERTS` is read once with a 1 MiB bound; unreadable/invalid configured trust fails preparation instead of silently weakening verification. Additional route CA remains scoped to its configured origin. System roots and valid explicitly trusted certificate chains work for HTTPS and WSS. `NODE_TLS_REJECT_UNAUTHORIZED=0` never disables verification. Rustls rejects a CA certificate used directly as a server leaf; custom deployments must present a correctly issued server certificate. No generated certificate or system trust installation is required.

## Plaintext source ingress

The native engine exposes a private authenticated loopback source to the selected launch plugin. It can register a bounded local HTTP/SSE/WebSocket route, update that route's upstream for future exchanges, close it, or submit a plaintext HTTP operation to the existing interception pipeline. `reserveRoute({upstreamBaseUrl, additionalCaPem?})` returns its private `baseUrl` synchronously; the plugin awaits `ready` before claiming activation. `reservation.update({upstreamBaseUrl, additionalCaPem?})` keeps that local URL while each active HTTP or WebSocket exchange remains pinned to the upstream and trust selected before the update. The optional certificate bundle is limited to 128 KiB and applies only to the registered upstream origin; an omitted update preserves it and an empty string clears it. The launch plugin supplies the integration at a verified client boundary and preserves the client's own authentication, network policy, certificate verification and cancellation. Core knows only generic source operations and exact-origin policy; client identities, endpoint selection and build-specific hooks belong to the launch plugin.

A source reports supported protocols, operations and path coverage individually. Unknown or unsupported paths remain unavailable. HTTP/SSE and WebSocket exchanges use the same owner and generation leases, limits and permission checks as other traffic registrations. The private route admits at most 4 HTTP and 32 WebSocket exchanges concurrently. This ingress installs no ambient proxy override, generated launch CA, system trust modification or TLS bypass.

## Native launch descriptor

Normal launch installs transparent client hooks only when its enabled Host catalog contains a plugin that both declares and has an explicit grant for `traffic.intercept`. Installing or enabling the first transparent traffic consumer during an unprepared session still requires restarting the client. Moving forwarding into Rust does not remove the Adapter's early-hook timing requirement. Explicit channels can independently start the native engine lazily, including a headless Core without an Adapter; that does not claim official-client attachment. An already attached client supports registration, retirement and hot updates. Safe mode skips plugin attachment. Preparing official hooks with no initial consumer remains a separate, unverified product change.

`Traffic::start_native()` prepares the engine and `Traffic::launch_descriptor()` supplies the unchanged descriptor before creating the client. It contains `source: {version:1,kind:'plaintext',protocols,operations,endpoint,routeBaseUrl}` and `environmentPatch: {set:{},removeCaseInsensitive:[]}`. The source endpoint carries a private token; `routeBaseUrl` contains an unpredictable loopback path prefix for synchronous route reservation. Native validates both loopback addresses, the bounded token and prefix, the offered operations and protocols, and the empty patch before passing the descriptor to a launch plugin.

Core owns native socket/task cancellation and a bounded transport cache. It does not change ordinary plugin Host heap settings or force garbage collection. The in-process engine shares Core's failure domain, so malformed records, concurrent operations, byte counts and handler lifetimes must remain bounded. Memory measurements use the complete engine and separately identify fixture/Host costs; bounded stress testing does not prove multi-day leak freedom.

The exact inherited client environment is retained, including its proxy, trust and bypass variables. The source descriptor is private and must not enter diagnostics. Native retires sockets/tasks and its private launch directory after the owned client exits. Attachment is a Native-only confirmation after an exact owned child integration, never a plugin registration result.

Desktop main-process hooks and local backend provider routing are separate integration paths. One path becoming available does not imply the other, nor browser, remote, worker, HTTP/2 or arbitrary-provider coverage. The launch plugin must preserve the original environment in backend tool children and report unsupported paths explicitly.

The Native prelaunch consumer selects exactly one enabled Host providing `codlet.client.launch@1` with `runtime` scope. This is an optional ABI phase of the same Host entry and immutable source generation; it is not a second plugin registry. Any plugin may provide it with explicit `host.process` and `cdp.raw` grants. `cdp.raw` gives privileged main-process access, including private launch descriptors, so it is not a restricted traffic-only permission. The provider does not need its own `traffic.intercept` grant: a separate enabled, authorized traffic consumer triggers the launch gate.

When that Host's effective capabilities contain only this one launch provider and no requirements, it is a Native-only launch entry. Core retains its source, trust checks and plugin identity but does not create an idle ordinary Host process or wait for ordinary Host readiness before activating its renderer. The reserved launch capability is never exported through service RPC. A Host with additional capabilities or requirements keeps the ordinary Host lifecycle as well as the optional launch phase.

The Host bundle exports `prepareClientLaunch({traffic, originalEnvironment, signal})`, returning `{arguments}`, and `attachClientLaunch({traffic, originalEnvironment, inspectorUrl, expectedPid, executable, signal})`. The fixed short-lived executor accepts only these two bounded private phases. Native permits exactly `--inspect-brk=127.0.0.1:0`; arbitrary, TLS and sandbox bypass flags are rejected. The attach result confirms `installed`, `exactChildVerified`, and one or more `activatedSources` entries containing a plugin-owned id plus explicit operation, protocol and path-coverage labels. `unsupportedSources` separately names unavailable paths with finite reason codes. Native validates bounds and subsets of the engine's offered operations and protocols; it does not infer complete traffic coverage or accept the former `configuredSessions` result. The launch plugin verifies the exact new child, installs its hooks before entry, waits for activated routes, and closes the inspector. Native reaps the temporary executor immediately after the handshake.

The inspector URL comes only from that exact child's dedicated stderr pipe, with a loopback host, ephemeral port and UUID path. Native neither scans ports nor reads shared logs. The stderr reader drains silently for the client's lifetime; handshake input is capped at 64 KiB and the endpoint-plus-attach deadline is ten seconds. A client fuse that prevents inspector startup therefore fails launch without declaring attachment. The complete authorization record is checked before and after each phase and at most one second apart during runtime; revocation exits the owned client through its normal quit/failure-cleanup path. `attached` means at least one declared source was installed; it does not prove every request or protocol path.

Rust error unwinding retains the engine and launch directory until the exact newly spawned client has been asked to quit and its retained process handle has been checked; failure cleanup may terminate that exact client. The client is not put in a kill-on-close Job, so independent updater descendants survive the normal update handoff. macOS update retirement waits for native traffic tasks before writing its cleanup receipt. A hard Core crash closes native sockets without running destructors; existing client hooks must fail closed. Automatic client recovery after such a crash is not currently verified or promised.

## Official Adapter

The official Adapter owns endpoint classification, task correlation and launch compatibility. Core does not know thread ids, providers or model names. Its Host SDK exposes reviewed task metadata to the consuming interceptor; it never borrows the Adapter's grants. Task-specific upstream selection uses the common traffic pipeline. The Adapter's general `codex.backend.write@1` task-configuration hook handles model/provider settings at thread start/resume, before backend auth and model setup. An optional `turn.start` registration chooses the model for each submission, including an already loaded task; provider changes remain limited to thread start/resume. The former dedicated `codex.backend.transport` layer has been removed. Existing active turns and established WebSockets are not migrated automatically; provider-specific continuation state remains plugin policy.

`context.traffic.inspect()` reports `available`, `listening`, `attached`, `activatedSources` and `unsupportedSources`. The source entries contain bounded non-secret coverage labels, not the private endpoint or request data. A client-specific Adapter must report each path unavailable until its exact child hook or route is installed. Fixture hashes and isolated probes are evidence only; they do not upgrade OAuth, Desktop, attachment or everyday-provider coverage.

## Explicit channels

`context.traffic.openSource({ upstreamBaseUrl })` creates a plugin-owned HTTP/SSE/WebSocket entrance through the same Core interceptor pipeline as Native sources. It returns `{ endpoint, close, dispose }`; await creation/removal to synchronize with the gateway. The URL is opaque and must not be persisted or logged. The upstream base accepts HTTP(S), unescaped ASCII path segments and no credentials, query or fragment. The caller needs `traffic.intercept`, `host.network` and the exact upstream origin grant. Each incoming exchange rechecks the source owner's current authority; interceptors retain their own independent permissions. Source removal, Host disconnection or generation retirement cancels its active exchanges. Core limits each owner to eight sources and all owners together to 32; Native launch routes have a separate 32-route allowance. This supports reusable local fixtures and plugin-owned traffic without exposing private launch-peer credentials. Success verifies the Core pipeline, not official-client hook coverage; the Native entrance must already be listening.

The existing `context.traffic.openChannel` and `openHttpChannel` APIs remain supported through thin JavaScript callback/stream bindings. A plugin may provide HTTP/SSE and WebSocket handlers and return its channel descriptor to an authorized consumer. Endpoints use private random paths on one native loopback listener, expire with the Host generation, and must not be logged or persisted. Declare/grant `host.process`, `host.network`, and each exact upstream origin. No `traffic.intercept`, Adapter, or extra Core-service capability requirement is added for channels. Channel lifecycle messages are a finite Host SDK endpoint set; Core selects the caller identity from the authenticated Host generation. Each owner has four channels and Core has 64. Synchronous `status()` remains a local projection updated by ordered events and receipts.

HTTP handlers receive a one-use body stream and may forward or return `{status, headers, body}`. Repeated headers remain arrays; SSE chunks are arbitrary byte chunks, not complete events. Each forward verifies current authority, has no implicit retry or redirect, and does not automatically copy incoming authentication. An explicit bounded `maxForwardAttempts` permits plugin-managed retries only after consuming/cancelling the prior response; replaying a consumed body requires the plugin's own bounded buffer.

WebSocket forwarding preserves ordering separately in each direction. Frame callbacks may pass, replace, or drop a message. Protocol conversion, model/provider routing and response repair belong to plugins. Cancellation reclaims local resources but cannot undo remote effects. The minimal [HTTP channel example](https://github.com/baoabaob/codlet/tree/main/examples/http-channel) and [Host types](../../types/host.d.ts) document usage.

Explicit channel sockets retain their original lifetime after the handler returns; the migration adds no fixed five-minute connection cutoff. Handler, handshake and individual peer-read deadlines still apply. Transparent interception retains its existing five-minute authorization lease bound. Cross-origin WebSocket rewrites also drop the original subprotocols, which can contain credentials; explicit forwarding must select protocols deliberately.

## Validation

Core tests exercise authenticated peer roles, exact-origin grants, cross-owner lease rejection, revocation and the real local TCP data plane. Runtime tests exercise bounded one-shot streams, cancellation, body/frame limits and callback ordering. Adapter tests exercise build gates, endpoint classification, compressed JSON rewriting and conflict-free thread configuration. A real client acceptance run must use a fresh private home and emit only bounded counters and finite error codes.

Build `cargo build --locked --features test-fixtures --bin codlet-traffic-fixture` before running the JavaScript traffic tests. This debug-only harness starts real Core policy and native transport with temporary plugin namespaces and in-memory credentials; it never reads the user's registry or credential store. Tests cover four concurrent 64 MiB HTTP responses and an 8 MiB WebSocket message in addition to ordinary traffic contracts. `scripts/measure-native-traffic.mjs` samples Windows Core memory/CPU with the pinned Node runtime as the external load generator. Its optional baseline argument points to a prior bundled worker extracted from Git; no old engine is included in production.

Historical controlled/live AppServer evidence is retained in Git at `d109d54`. It used independent profiles and verifies a backend path, not installed Desktop coverage. Source tests and `scripts/verify-official-main-owned.mjs` report individual path results from an isolated owned client; they do not upgrade unsupported paths. Keep credentials, raw traffic, dated run journals and memory reports outside the source repository.
