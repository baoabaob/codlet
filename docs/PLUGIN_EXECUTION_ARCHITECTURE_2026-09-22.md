# 插件执行与回收架构权衡 · 2026-09-22

状态：设计建议，尚未改变生产运行时、插件 API 或热重载行为。用户要求先从产品和主架构评估冗余，并以不削弱插件能力为前提。本页修订此前容器实验报告中的公开 Worker 实施设想；实验数据本身不变。

## 建议

**暂不增加长期公开的 Worker 运行模式。维持一套插件身份、依赖、权限、通信和生命周期体系，复用已有 Host；下一步只验证可销毁的完整自有 UI 视图，同时保留直接扩展官方页面的能力。**

这仍有不同执行位置，复杂度不会凭“统一 SDK”四个字消失。目标是让不同位置承担不同职责，避免旧 renderer 和 Worker renderer 各自维护一整套重叠的 UI、RPC、错误处理和开发工具。

800 轮 Worker 实验支持“固定的受信任接入代码 + 可销毁实例”的原则。它只挂载了三种固定控件，不能证明 Worker 是正确的产品边界，也不能证明任意现有插件可以原样迁移。

## 保持的产品边界

- 仍是一种插件包、一次安装、一份启用状态和权限记录；普通用户不选择执行引擎。
- 自定义 UI 保留完整 JS、React/其他前端框架、HTML、CSS、组件、DOM 引用和视图内同步事件处理；官方 UI 仍为可选项，不把 UI 限制成固定控件清单或 JSON 表单协议。
- 修改官方页面 DOM、`ui.mainWorld`、`cdp.raw`、`host.process` 继续是可明确授权的能力上限。第三方作者不因不是官方插件而被禁止使用这些权限。
- 纯 UI 插件不被强制搬进 Node Host，不因此增加 `host.process` 或 `cdp.raw` 权限。需要后台、系统或 Node 能力时才使用现有 Host。
- Core 继续提供通用能力及拥有者/资源管理；官方客户端的私有 API、React 树、路由和版本知识仍由 Adapter 负责。新的透明流量通道复用正在开发的 Core/Host 能力，不因 UI 改造再实现一套网络出口。
- 现有插件继续工作。将同步接口改成异步、改变工具栏位置、缩小模态框覆盖范围、要求更多权限或减少可用框架，都属于可见兼容变化，不能作为内部重构悄悄带入。

## 为什么不立即增加 Worker

1. **可销毁的后台执行器已经存在。** Host 每代使用独立 Node 进程，已有启动、撤权、取消、有限清理、超时/崩溃与最终进程回收。新 Worker 对无 DOM 的业务执行会重做其中不少机制；它的独立线程有价值，但当前没有证明需要把这种实现细节升级成第三种公共 ABI。
2. **现有 UI 契约并非声明式控件协议。** `RendererUi` 直接提供 React、`HTMLDivElement`、`createPortal`、`flushSync`。自定义组件、第三方 DOM 库和闭包不能直接通过结构化消息传输。实现通用远程 DOM/React 将成为一项新的兼容工程。
3. **官方 GUI 已经使用这些复杂能力。** 搜索与标签候选使用同步布局、焦点、selection、滚动；内容、原生工具栏和 overlay 由同一 React 树协调。Worker 三控件原型没有覆盖它们。
4. **Worker 也不能替代页面 Adapter。** 官方对象、React Fiber、原生路由和传输 hook 仍需要页面里的接入代码。因此旧页面路径不会自然消失，只会再增加一条 Worker 路径。

依据：[现有 JS 插件格式与 Host](JS_PLUGIN_RUNTIME_2026-09-09.md)、[UI 类型契约](../types/renderer-ui.d.ts)、[页面装配](../frontend/src/page.js)、[容器实验](RENDERER_CONTAINER_EXPERIMENT_2026-09-22.md)。浏览器语义可参照 [Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)、[iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)；[Chrome 页面脚本](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)也明确区分页面 DOM 访问与通过消息取得其他能力。这些资料不能替代 Codlet 的实机验收。

## 目标分工

| 职责 | 执行与能力 | 生命周期 | 是否新增平行业务运行时 |
|---|---|---|---|
| 后台/系统逻辑 | 现有 Host：Node、Core services、权限范围内的系统与流量能力 | 已有进程监督与代次回收 | 否，复用已有机制 |
| 插件自己的界面 | Renderer 完整自有文档；优先验证 sandbox iframe，而非 Worker 驱动有限组件 | 文档及其 owned 资源可销毁；完整 GUI 尚待验证 | 改造现有 UI 承载，不另设 Worker SDK |
| 接入官方客户端 | Adapter 的少量页面代码负责路由、入口、挂载位置和经过适配的原生调用；Core 管理通信与资源归属 | 目标窗口生命周期，业务实例通过受控通信连接 | 基础设施，不向每个插件暴露任意代码执行桥 |
| 任意页面扩展 | 保留现有获授权的 isolated/main-world 注入及 raw CDP | 与所修改页面共享部分寿命；清理有明确限制 | 保留能力边界，不谎称可硬销毁 |

例如，插件自己的设置页面适合自有文档；隐藏官方额度提示仍属于页面扩展；API 切换通过 Core 流量通道和 Adapter，按需求由 Host 持有后台逻辑。同一插件可以组合所需部分，不要求所有插件编写所有入口。

自有视图内应由插件自己的代码直接操作自己的 DOM。父页面接入层只接收有边界的注册、挂载、主题、语言和动作消息，不接收任意插件函数后替它在父页面执行，也不把父 DOM 或 React 对象传给子文档。其中特别要区分两件事：父桥代码受信任，不代表只有官方插件能够申请页面权限；任意页面插件仍通过独立、显式授权的路径运行。

所有位置共用一份 Core 的有效授权与 owner 记录，至少包含插件身份、来源/代码身份、代次、目标和文档时期。传输层负责不同位置的编解码，不能重新维护自己的授权真相。视图入口得到的 Target 由 Core/Adapter 根据 owned 挂载关系签发，不能让插件自报父 target，也不能迫使普通 UI 为取得作用域去申请 `cdp.raw`。

## 不回避的限制

**目前没有证据证明在当前 CDP 接入方式下，可以同时提供任意同步页面注入、旧实例严格隔离，以及所有插件无限次无重启热替换且所有环境/副作用必然回收。**

isolated world 共享页面 DOM；main world 更与页面共享 JS 环境。无论 Host 进程还是 Worker 被销毁，都不会自动撤销此前写入页面、磁盘或网络的任意副作用。一个插件把闭包交给原生对象、永久改写原型或保存不可逆状态之后，单靠卸载其入口无法证明已经完全清理。

因此需要区分：

- **撤权完成：**旧实例不能再使用 Core 管理的能力，pending 请求、代次绑定的 port、队列和受管资源终止。
- **合作清理完成：**插件及 SDK 按契约卸载已登记的页面资源；不能因此断言浏览器 realm 已消失。
- **执行环境被销毁：**Host 进程或自有子文档已确实结束，并验证不再被外部引用保留。
- **页面级强清理：**任意直接注入的旧世界或副作用需消除时，兜底应是经验证的受影响 WebContents/窗口销毁重建，或者客户端完整退出再启动。此前压力实验的普通 `Page.reload` 没有清掉旧 world，因此不能把 F5、路由跳转或普通文档刷新当作这项保证。

现有 `RendererReloadRequired` 可以作为状态表达的起点，但重建窗口的实现、草稿与运行中任务的保存、受影响窗口的范围都需要单独验证。这是生命周期产品行为，不在此次设计中直接改成“所有更新必须重启”。当前热重载行为先保留，累计风险也如实保留。

同样，不把停用/重新启用悄悄改为在旧 world 中恢复旧实例。现有 facade 退役后不可重新激活；将其复活会改变代次隔离语义。合作式暂停/恢复与卸载/重新授权属于不同操作，不能混称。

## 方案比较与当前选择

| 选择 | 功能上限 | 回收收益 | 主要代价 | 当前判断 |
|---|---|---|---|---|
| 旧 renderer + 公开 Worker 双轨 | 通过保留旧路径维持上限 | 仅迁入 Worker 的部分受益 | 重叠 ABI、UI 协议、状态机、文档、测试，旧问题仍在 | 不推进公开化 |
| 所有插件强制 Worker 化 | 直接页面与完整同步 UI 语义不等价 | 业务容器容易终止 | 实质能力/开发体验改变，或建设通用远程 DOM | 不符合用户前提 |
| 保留现状，仅以重启释放 | 不减少当前能力 | 只有退出后释放 | 日常投入最小，但高频热重载问题持续存在 | 当前兼容基线，不能当最终优化成果 |
| 复用 Host，先验证可销毁完整 UI，保留页面扩展 | 保留能力上限；迁移需逐项证明体验等价 | 自有 UI 的环境可回收，页面 hook 有明确寿命 | 自有 UI 与页面接入仍有两种寿命，需解决跨文档交互 | 推荐的演进方向，先验证再迁移 |

## 下一项投入及验收门槛

下一步是**完整 GUI 的自有视图可行性验证**，不是继续扩展 Worker 的控件清单，也不直接改默认 manifest 执行方式。先验证最容易造成产品退步的内容：

1. 任意 React 组件、DOM refs、同步布局与 selection；自定义 CSS 和不使用官方 SDK 的视图；无需新增 Host 权限。
2. 保持现有侧栏/路由、原生 toolbar 位置、菜单越界显示和模态框覆盖范围；鼠标、IME、Tab/Escape、焦点返回、主题与 i18n、缩放与辅助窗口。
3. 完整 GUI 的搜索/标签、市场、安装风险确认、依赖移除、更新、设置、新任务/skill 等流程，与旧实现逐项对照。
4. 旧 port、旧回调、伪造 generation、晚到请求、视图崩溃/导航/超时后不能重新取得授权；由 Core 而非已撤权插件承担最终受管清理。
5. 最少数百次真实完整 GUI 重载与长时间空闲，同时检查 context、DOM、监听器、pending/队列、JS 堆及原生私有内存；Windows/macOS 分别给出证据。

**工具栏与 overlay 是首个门槛。**一块隔离 iframe 不能任意越界绘制，多块 iframe 也不能共享同一个同步 React/DOM 树。候选方案包括多个有所有权的完整视图 surface，或有限的 Adapter 原生控件接入，但这都需要成本和体验对照。若必须把控件挪位、限制自定义组件或扩大权限才能实现，则该迁移不算通过；保留当前运行方式，重新比较收益与代价。

验证通过后，才迁移官方 GUI 并逐步推荐新的自有视图入口；旧页面扩展用于确实需要页面能力的插件，兼容适配不再复制一套完整服务实现。Worker 实验继续保留，未来若出现不宜申请 Host 权限、又需要可强制结束的重计算需求，再以独立需求评估其是否值得公开。

本次没有启动生产实现，也没有改变另一个任务正在开发的透明流量接口。两名独立审查代理的源码复核均认为当前完整 Worker 等价性不成立、公开第三运行模式会重复现有能力；本页据此收敛实施范围。
