# 下一主线：Codlet 透明流量接管

状态：已确认目标，进入接入路径验证；尚未实现或验收透明接管。现有 `openChannel` / `registerThreadTransport` 的成功测试不计入本计划的覆盖结果。

## 目标与边界

通过 Codlet 启动并启用相应插件后，保持原有官方登录、模型配置和任务使用方式，让插件介入真实出站请求与入站响应。当前任务及历史任务在此后产生的新连接/请求均在目标范围内；首次启用可以要求重启客户端，不承诺把已经传输的连接无损迁移。

优先级：

1. 模型请求：HTTP/HTTPS、SSE、WS/WSS；读取原始头部/正文/消息，修改请求和响应、阻止、合成响应、改换转发目的地。
2. 模型列表及相关服务接口。
3. 会话附件上传与下载。

暂不覆盖外部浏览器、任意工具子进程，以及绕过已接入网络栈的长尾流量；Linux 仍不进入本轮平台适配。Core 不实现特定 API 网关的业务逻辑，也不把传输事件改写等同于“对话保证不断”。

## 已核实的差距

- 官方 Adapter `frontend/src/desktop/transport.js` 第 20 行的探测结果明确为 `activeTurns:false`、`existingLoadedThreads:false`、`officialOAuth:false`。
- 第 104 行为新建/恢复请求写入一个新的 provider，且 `requires_openai_auth:false`。这是显式通道接入，不符合本次保留原官方流量路径的要求。
- Core `runtime/host-traffic.cjs` 已有转发、字节流和 WS 双向消息处理，保留可复用部分。
- 本地官方源码快照 `8d32abc` 的 `core/tests/suite/responses_system_proxy.rs` 验证了模型 Responses HTTP 请求使用系统代理的场景；该测试显式启用了 `RespectSystemProxy`，并修改了测试 provider。此快照尚未证明与当前 `0.155.0-alpha.9.2` 二进制一致，因此不能据此声称默认官方 HTTPS/WSS 已能接管。

官方文档确认 `CODEX_CA_CERTIFICATE`（回退到 `SSL_CERT_FILE`）可为登录、HTTPS 和安全 WebSocket 配置 PEM CA。它提供了进程专属信任的可行性线索，但没有证明桌面所有请求均经过该路径。参见 [官方认证说明](https://learn.chatgpt.com/docs/auth#custom-ca-bundles)、[环境变量说明](https://learn.chatgpt.com/docs/config-file/environment-variables)。

Electron `webRequest` 提供取消/重定向、请求头和响应头等拦截节点，不能据其握手事件直接推断具备完整响应正文与 WS 双向消息替换能力。桌面正文流量需要独立验证接入点。参见 [Electron WebRequest API](https://www.electronjs.org/docs/latest/api/web-request)。

## 实施顺序与退出条件

### T0：确认实际请求出口

- 固定当前官方客户端/后端的版本及文件哈希，定位桌面、官方后端、模型接口和附件接口分别使用的网络栈。
- 分别验证加密前/解密后挂钩和进程范围代理路线；优先复用受支持的进程配置，不能提前把某一种路线当作可用成品。
- 先在本机受控 HTTP/SSE/WS/TLS 服务中验证当前官方后端的代理路由、证书验证、原始目的地址保持和协议选择。成功的模拟服务结果与官方登录路径验收分开记录。
- 检查已有企业 CA/代理的合并与上游代理继承，以及代理本身递归进入自己的问题；不得用关闭 TLS 校验代替信任配置。
- 形成覆盖矩阵：进程/功能/协议/接入点/实验证据/限制，未验证项保持未知或不支持。

当前真实桌面实验另有前置问题：性能测试新编译的 `codlet-lab.exe` 被 Defender 隔离。先核对触发的启动行为；不关闭防护或添加排除项来取得验收结果。独立协议夹具和只读源码核对可继续。

### T1：Core 通用拦截基础设施

- 启动前就绪的进程范围入口；配置只作用于 Codlet 创建并持有的客户端/后端，明确启动失败与入口异常时的行为。
- 拦截器声明过滤范围、优先级和拥有者代次；定义多个插件重写、阻止、合成响应时的确定顺序和冲突结果。
- HTTP 头部、一次性请求/响应流、SSE 原始字节流、WS 文本/二进制消息的公共契约；允许流式处理，不要求整包缓冲。
- 复用现有转发与流管理；统一背压、并发/大小/队列预算、决策超时、取消和异常清理。
- 原有目的地址的认证按原语义保留；更改 origin 时不自动泄露原站认证给新站点。插件读取敏感头部或改换上游需有明确权限和授权范围。
- 常规日志只记录计数、耗时、错误码与覆盖状态，原始令牌、正文、附件和私有 URL 参数不写入诊断。
- 不把流式 API 的管理 RPC 保持成无界长事务；禁用、撤权、重载和进程退出释放所属的流、连接与缓冲。

### T2：官方 Adapter 自动接入

- Adapter 封装当前构建的桌面/后端路径与 Codex 语义，向插件提供统一的拦截注册入口。
- Core 不认识线程、供应商和模型；Adapter 提供可验证的语义元数据，未知关联不得猜测。
- 既有会话的新流量同样生效；UI 如实显示首次生效是否需要重启及已经覆盖的协议。
- 构建漂移或接入失败保持明确的不可用状态，避免“注册成功”实际没有流量经过。

### T3：插件与旧接口迁移

- 盘点所有 `openChannel`、`registerThreadTransport`、示例和官方插件的依赖。
- 以直接注册拦截器作为主要用法，先迁移已有使用方，保留可复用的内部流与转发实现。
- 确认无使用方后再撤销重叠的公开通道接入流程；原有功能与权限行为均有回归覆盖。
- 同步 Core/Adapter 类型、能力探测、示例、安装权限文案与运行时 Codlet skill。

### T4：真实链路与性能验收

| 项目 | 必须留存的证据 |
|---|---|
| 官方登录与原会话 | 原 provider/登录不变，拦截器接收到真实请求/响应；不记录凭据 |
| HTTP | 请求与响应正文分别改写；阻止、合成响应和上游改换的确定结果 |
| SSE | 分片/合并边界、逐步输出、慢消费者与中途取消 |
| WS/WSS | 客户端到服务端及反向消息各自改写，文本/二进制、关闭与异常处理 |
| 历史任务 | 启动前已存在的任务，其后新请求经过拦截器 |
| 生命周期 | 插件禁用/重载/撤权/崩溃后，所有连接和缓冲按约定处理 |
| 模型与附件 | 分接口证据，不能由模型请求通过推断其通过 |
| 性能 | 原路径、启用但无处理器、透传处理器、正文/WS 改写四组；新增延迟分位数、CPU、私有内存、队列峰值与释放后残留 |

在上述真实路径证据齐备前，能力探测不得声称支持官方 OAuth、现有会话或桌面全流量。性能口径沿用 [本次性能分析](PERFORMANCE_2026-09-21.md)，原生进程与模拟 JS 测量分别报告。
