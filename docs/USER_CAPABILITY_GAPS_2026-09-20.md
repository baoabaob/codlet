# 从用户和插件作者出发的能力缺口

状态：2026-09-20 的设计脑暴，依据本工作树公开类型、实现和开发文档。仅维护本文；未运行客户端、测试或发布。用户已明确本次基础支持必须覆盖官方客户端使用的 HTTP(S)/SSE 与 WS/WSS，由 Adapter 抽象统一接入。并行实施状态以 [实施计划](TRAFFIC_INTERCEPTION_PLAN_2026-09-20.md) 和后续验收记录为准，不能从计划推导为已交付。范围为 Windows 与 macOS，Linux、打包及发布不在本轮范围。

## 判断

最值得先补的不是更多内置业务，而是**真实请求可接入、资源可归属、长流可取消、操作结果可判断**。这些基础能力能让插件作者自行做 API 切换、错误处理、资料连接、任务看板和自动化。

用户的核心诉求可以表述为：“我想写一个插件，在需要时改变实际发出的请求及返回内容，尽量保持任务可继续。”这里有两个不同目标：请求处理能力可以由通用通道提供；任务是否仍能正确继续，取决于协议、客户端状态和已经发生的副作用。不能把 HTTP 成功、流正常关闭、工具执行成功或任务完成视为同一事实。

用户已明确只需要基础支持。供应商排名、健康检查、重试次数、错误屏蔽、协议转换、恢复文案和业务 UI 均由普通插件决定。本文不参考或移植外部网关产品，也不把某个产品的功能表转成 Core 待做清单。

## 已有地基，以及容易被误读的边界

| 现有证据 | 已能做什么 | 不能据此声称什么 |
| --- | --- | --- |
| [Host 类型](../types/host.d.ts)，[Core RPC](CORE_RPC_2026-09-10.md) | Host/renderer 能互调；有 capability、调用者身份、generation、Runtime/Target scope、deadline 和取消链 | Runtime 不是用户全局设置；Target 是页面生命周期，不等于任务或模型请求会话；普通 RPC 不是长流或持久队列 |
| [原始 CDP 与 Core 边界](CORE_EXTENSION_BOUNDARY_2026-09-09.md) | 插件可自行选择目标、注入、订阅原始事件；官方 Adapter 可选 | Chromium 网络可见性不证明能截获由 Native/AppServer 发出的模型 HTTP 请求；公开 raw 能力也不等于任意 OS 网络接管 |
| [现有网络实现](../src/os_broker/network.rs)，[OS broker](OS_BROKER_2026-09-10.md) | 受 origin 授权的 GET/HEAD；完整 UTF-8 文本响应；请求有界且可取消 | 没有现成的 POST 正文、双向长流、监听端点或实际模型请求接入；这不是全客户端代理 |
| [Desktop 类型](../types/codex-desktop.d.ts)，[适配器契约](DESKTOP_ADAPTER_DEVELOPMENT_2026-09-10.md) | 使用已有 Desktop 连接读任务/事件，启动、引导、打断已加载 owner 任务；提交前改写文本/追加上下文 | `providers.list` 不包含切换 API 地址的能力；`preSubmit` 不修改真实网络目的地或响应；提交回执不证明完成 |
| [UI 类型](../types/renderer-ui.d.ts) | 官方组件、整页、页面工具栏、可编辑的新任务草稿和资源清理 | 不等于任意消息旁按钮、输入框插槽、全局命令或后端历史修改 |
| [包存储实现](../src/managed_storage.rs)，[README](../README.md) | 包替换有所有权和恢复记录，插件数据与包代码分开 | 包管理事务不等于插件可用的配置/KV/密钥 API；现有公开 Host/renderer context 未声明这类统一接口 |
| [诊断包](DIAGNOSTIC_BUNDLES.md) | 有来源的运行时诊断、精简导出、避免导出凭据和会话内容 | 没有据此证明每个模型请求可追踪到路由决定、上游尝试、流阶段和最终业务结果 |

Host 已能运行受信任的 Node 代码，因此很多缺口是“缺少统一的受管契约”，不是“技术上禁止插件自行实现”。例如插件可以自建网络服务或文件存储，但需要自己承担地址发现、跨平台、撤权、进程退出、并发及恢复。Core 的增补应减少这些重复工作，同时保留 raw 路径；不能因此宣称 Host 是 OS 沙箱。

## 优先级与分工

P0 表示会阻止核心用例成立或导致错误结果的基础缺口；P1 表示多个插件都会需要的复用能力；P2 表示应由实际插件需求再推动的扩展。以下 API 概念是建议，未冻结名称和 schema。

### 1. 我改了 API，真正请求到底去了哪里？——P0

**证据与边界。** 现有 `preSubmit` 只处理文本和附加上下文，`host.network.fetch` 是插件自身请求，raw CDP 的覆盖由目标决定。当前 HTTP(S)/SSE 与 WS/WSS 通道方案正补显式接入路径；两种传输均是本次必需支持，具体线程、登录模式和已建立连接的覆盖仍须实证。

**所需分工。** Core 提供与具体应用无关的 HTTP(S)/SSE 和 WS/WSS 受管通道、监听端点及请求/响应或双向消息控制权，返回真实可查询的通道状态。官方 Adapter 找到已有 Desktop 连接支持的接入点，提供统一的接入与状态接口，并公开“新任务、恢复任务、已加载任务、进行中请求分别支持什么”，私有 provider/config 字段留在 Adapter。普通插件选择服务、显示切换入口并决定何时切换；统一接口仍须保留底层传输类型与实际限制。

**最小验收。** 两个本机上游分别记录请求；同一用户动作在指定接入后只到达所选上游，携带预期方法、正文和头。HTTP(S)/SSE 与 WS/WSS 分别完成实际请求/消息往返，并验证同一 Adapter 接入入口。未接入的任务明确显示未覆盖。仅修改 UI 标签、插件自己的测试请求成功或第二个 AppServer 成功均不算通过。

### 2. 只切当前任务，其他任务继续用原服务——P0

**证据与边界。** Core 已有 Runtime/Target scope，但 Desktop 文档明确把 backend/thread 生命周期留给 Adapter。窗口中切换任务、同一任务在多个窗口打开、进程重启都不能靠一个页面 Target ID 表达。`providers.list.selected` 也不足以证明本次请求的实际路由。

**所需分工。** Core 允许通用的不透明资源句柄关联 owner/generation 和租约，不理解 threadId。Adapter 映射客户端真实任务/连接身份，报告接入生效时机。普通插件定义“一次请求、当前任务、后续新任务、用户默认”的规则及优先级；全局默认是插件配置，不是 Core Runtime scope 的别名。

**最小验收。** A/B 两任务分别使用 X/Y；修改 A 的下一请求规则不改变 B，也不迁移已发出的请求。导航与多窗口不串任务。规则变更产生可读取的版本；已接受请求固定其规则快照，重载后旧句柄不能修改新请求。若底层只支持新建/恢复时配置，就明确拒绝不支持的热切换。

### 3. 插件能处理大请求、长响应和流，而不是等全部结束——P0

**证据与边界。** 既有 broker 累积整个 UTF-8 body 后返回；Core RPC 最长 15 秒并有 JSON 大小和并发上限。它们适合有界操作，不宜直接改成一次持续数分钟的模型 RPC。

**所需分工。** Core 本次同时提供 HTTP(S)/SSE 字节流和 WS/WSS 双向消息资源，统一归属、读写、背压、有界缓冲、取消和结束状态；按传输类型保留 HTTP 响应阶段与 WS 握手、文本/二进制消息及关闭语义。短 RPC 控制长资源，沿用身份和撤权，而不是放大所有 RPC 的默认超时。SSE 的字节可以原样流经 Core；Codex 私有事件映射归 Adapter，Responses/Chat/其他协议转换和业务事件修复归普通协议插件。WS/WSS 基础传输是当前交付项，不以强制客户端退回 HTTP 替代。

**最小验收。** 上游未结束时下游已收到多个分块；多字节字符跨块、二进制 body、慢下游、超大 body 和读取中取消均有确定行为，内存受界限约束。SSE 事件边界不能靠网络 chunk 边界猜测。WS/WSS 验证双向文本/二进制消息及其顺序、分片组装、Ping/Pong 保活、关闭码/原因、异常断连和两方向背压；握手失败保留真实 HTTP 状态，升级成功后不再套用普通 HTTP body 的终态。HTTPS/WSS 均执行 TLS 证书验证。

**统一通道的两项优先审查。**

1. **长连接身份与切换生效点。** 已有 Core RPC 绑定 generation、Target/document epoch 且有短 deadline；新长流应拥有明确租约，不能靠保持一次 RPC 未完成或重新续预算生存。Adapter 必须区分页面、任务、逻辑模型请求和可能复用的 WS 连接：切换“下一请求”不等于能迁移现有 WS；若需换连接，应显式报告，并保持进行中请求的真实取消/完成状态。
2. **共同控制面与不同数据边界。** 统一接入、授权和生命周期不应抹平 HTTP 字节流与 WS 消息的区别。握手前的 origin/认证检查、握手后的双向有界队列、消息类型/顺序、关闭传播都须贯通；升级失败不能伪造成已建 WS，正常 socket 关闭不能伪造成 Codex 回合完成。私有请求 ID、工具调用和业务终止事件仍由 Adapter/插件解释。

### 4. 错误处理插件可以介入，但只有一个确定的处理结果——P0

**证据与边界。** 现有提交拦截器已有顺序、超时、启停、统计与清理，适用对象仅为提交草稿。capability 冲突管理能避免重复 provider，却不负责所有插件的直接 patch 冲突。

**所需分工。** Core 的通用请求资源需要明确控制权及一次性状态推进：观察、接管、转发、直接响应、拒绝，各阶段能做什么必须可查询；超时或旧代迟到回调不能重新提交。第一版可选单一写入 owner，加只读观察者；只有确实需要多级处理时再增加可声明的有序链。普通插件决定是否处理某状态码、改写内容或尝试另一上游，Core 不默认吞错或重试。

**最小验收。** 两个插件争夺写入权时得到明确冲突或明确顺序，不能各转发一次；处理器超时后迟到的“转发”被拒绝。普通插件显式构造响应时结果可传递，但记录为插件响应，不能伪称来自原上游。禁用处理器后旧回调不复活。

### 5. 断流后能继续到什么程度，必须知道已经发生了什么——P0

**证据与边界。** Desktop 已有 turn/item 事件和历史读取，`turns.interrupt` 返回提交回执；文档明确已发写操作不能靠 RPC 取消撤销。现有 API 没有模型 HTTP 尝试与 turn/tool 执行之间的完整对应关系。

**所需分工。** Core 报告通用传输事实：是否开始发送请求、响应头是否提交、已交付字节、正常 EOF/取消/断流、结果是否未知，以及上层可串联的关联 ID。Adapter 如有可靠依据，再把传输与原生 turn/item/call ID、完成/失败状态关联；缺失证据就保留未知。普通插件据此制定重试、续接、提示或停止策略。

**最小验收。** 分别在发出前、上游已收到但尚未响应、输出了部分文本、输出了工具调用后断流。每种状态可区分，Core 从不隐式重放。已经向下游交付的两份模型流不直接拼接成一份；没有上游幂等/续传及客户端语义证据时，不承诺无损恢复或 exactly-once 工具执行。

“没有收到响应”不证明上游没接受请求；“没有输出文本”也不证明没有工具副作用。调用者取消、客户端 UI 关闭和服务器停止工作同样是不同事实。让任务保留历史、草稿和明确的继续入口，是有用的恢复体验；伪造 `completed` 只会掩盖失败。

### 6. 切换地址时不能把另一服务的认证一起带走——P0

**证据与边界。** 既有 broker 有 origin 授权和禁止路由/逐跳头覆盖的限制，但公开类型没有密钥存储/凭据绑定接口。`providers.list` 有意不返回原配置和凭据。受信任 Host 可以自行访问 OS，不能把新 API 的限制描述成恶意插件隔离。

**所需分工。** Core 在受管转发上逐次检查已授 origin、隔离本地通道认证，跨 origin 不默认复制认证头；资源调用仍绑定插件身份和 generation。后续可提供通用的系统密钥存储封装及不透明引用，命名空间由 Core 判定；凭据选择、轮换策略和登录 UI 属于插件，Codex 官方登录语义属于 Adapter。不要让 Core 读取或改写 Codex 登录文件来“顺便切源”。

**最小验收。** 切 A→B、跨源重定向和请求失败导出诊断时，A 的认证及本地接入凭据均不会出现在 B 或日志中；B 未授权时请求被拒绝。插件更新保留用户明确允许的凭据归属，来源变化不能仅凭相同插件 ID 静默获得旧凭据。

### 7. 我点了停止或停用了插件，正在等的请求也应收尾——P0

**证据与边界。** 已有 generation 退休、取消链、有限 cleanup 和 `cleanup_incomplete` 语义可复用；现有文档也没有承诺任意外部副作用回滚。新增监听器和长流必须纳入这套生命周期，不能只靠插件 `deactivate` 自觉清理。

**所需分工。** Core 持有连接/流/监听端点资源和有界结束预算，区分取消已请求、资源已释放与无法确认。Adapter 传递原生取消并保持 Desktop 状态真实。普通插件决定停用前是否提示或允许现有请求在明确期限内结束；不得用“保持任务不中断”无限阻塞停用或撤权。

**最小验收。** 用户取消、停用、撤权、reload、Host 异常退出分别触发一次收尾；不接受新流，已取消回调不能创建上游请求，旧端口可释放。无法确认远端停止时如实返回未知，不显示“任务已取消且无副作用”。Windows/macOS 分别核验资源退出，不能平移 Windows 结论。

### 8. 我想知道慢在哪、谁改了内容、为何失败——P0 最小观测，P1 完整开发工具

**证据与边界。** Doctor、导出和提交拦截器统计已存在，能作为统一入口；它们不是网络请求追踪器。诊断导出目前有明确的精简字段和脱敏边界。

**所需分工。** Core 为受管资源提供有界的阶段、耗时、字节量、owner/generation、决策/尝试关联及结束码；插件可报告带来源的扩展诊断，但不能覆盖基础事实。Adapter 补充可验证的客户端关联和兼容性状态。插件制作看板、费用统计、提示和更详细的本地调试视图。

**最小验收。** 一次失败能判断发生在接入、插件决策、连接上游、首响应、流读取或客户端取消阶段，并找到责任插件；缺少样本明确显示缺口。默认诊断不包含正文、工具参数、API key 或完整认证 URL；调试采样须有可见开关、限额和关闭后的确定行为。

### 9. 插件设置和用户数据应跨更新保留，多窗口不互相覆盖——P1，路由规则上线前需最小版本

**证据与边界。** 包和数据已分开，包安装有事务；公开 Host/renderer 类型仍没有统一的插件配置/KV API。Host 可自行读写文件，renderer 也能自行使用页面存储，但这种做法没有统一命名空间、迁移和多窗口并发契约。

**所需分工。** Core 提供通用数据目录身份或最小持久存储契约，至少包含插件命名空间、版本/CAS、原子提交、配额、变更通知和卸载保留/删除语义；配置 schema 和版本迁移逻辑归插件。较大业务数据库不必强制搬入 Core。凭据与普通配置分离，导出/同步不能默认包含秘密。

**最小验收。** 两窗口编辑同一规则时，一方得到明确冲突或合并后的版本，不静默覆盖；插件更新后用户配置仍在；迁移失败保留可恢复旧数据；停止/移除包与删除用户数据分别有明确结果。

### 10. 几个插件要协作，但不能靠猜 DOM、共享全局变量或一直轮询——P1

**证据与边界。** 已有版本化 capability、调用者认证、依赖图、跨层 RPC；不应再造一套插件总线来替代它。当前 `notify` 不是持久消息队列，公开 SDK 没有通用的带背压、游标和快照补齐的跨插件订阅契约；Desktop 自己的事件缓冲仅面向该 Adapter。

**所需分工。** 在现有 RPC 上补通用订阅资源或推荐实现约定，声明流归属、顺序、最大积压、gap、退订和 provider 换代行为；只有复用场景证明必要时才进 Core。Adapter 对任务事件提供快照与增量映射；普通插件定义路由配置、备注、工具状态等业务事件和选择哪个 provider 的产品策略。

**最小验收。** 路由配置插件与状态栏插件通过公开 capability 协作；慢消费者能发现 gap 并重新取快照；provider reload 后旧订阅结束，新代不会继承旧授权或收到错代消息。观察者失败不导致请求被重复发送。

### 11. 在原来工作的地方调用插件，而不是每个插件都开一个大面板——P1

**证据与边界。** 已有官方组件、侧栏整页、工具栏、新任务草稿和 i18n。消息旁操作、任务状态位置、输入框附件/动作、快捷键和命令发现尚无公开统一契约；原始 DOM 当然仍可自行使用。

**所需分工。** Core 只提供通用注册、资源归属和清理，不硬编码 Codex 菜单。官方 UI Adapter 按已核验构建公开少量稳定 surface/命令上下文，缺失位置能独立降级。普通插件提供按钮、表单、命令和内容；不把供应商选择器写入 Core 管理 UI。

**最小验收。** 普通插件在当前任务可见位置显示“下一请求使用哪个服务”，不显示未经确认的进行中路由；重载、导航、主题/缩放和窄窗口后无重复节点/快捷键。某个插槽失效不拖垮已有侧栏页面或 backend 能力。

### 12. 我想做完成通知、长任务看板、排队或定时执行——P1/P2

**证据与边界。** Host 能运行 JS 定时器，已有 task 事件可驱动观察型插件；RPC 是短调用，现有管理操作 receipt 服务于插件生命周期，不等于普通插件的持久作业。Core 关闭后没有依据承诺插件继续运行；Desktop v1 的写入要求已加载 owner 任务。

**所需分工。** 若多个插件确实需要，Core 可补通用作业句柄、归属、配额、取消、进度及可查询终态；持久排队需单独定义重启后的确认语义。Adapter 仅提供真实任务生命周期和经审核的创建/恢复/提交入口。通知、定时规则、并发策略和何时发起模型任务归普通插件，不能因为恢复一条队列就默认重放副作用。

**最小验收。** 两窗口观察同一完成事件只执行一次插件业务通知；关闭面板不必结束明确归 Host 的观察作业，停用插件则必须结束。Core 重启后未知执行结果保持未知，不能自动重新发送模型任务。“应用关闭后仍执行”须另有明确执行环境，不能由普通定时器冒充。

### 13. 资料、附件和结果导出应有可复用通道——P1/P2

**证据与边界。** 现有文件 broker 是有界读取，Desktop 写入是文本，`preSubmit` 可追加文本上下文；没有统一的用户选文件、受管写入/原子导出、附件提交和大对象传递契约。Host 仍可自己做，但跨平台路径、清理和 UI 需重复实现。

**所需分工。** Core 可提供通用文件选择后授权、受管写入/原子替换、文件资源句柄和大小限制；大数据不塞进 JSON RPC。官方 Adapter 在原生格式得到核验后提供附件/富输入能力，保留来源和生命周期。摘要、知识库、脱敏、导出格式及是否上传由普通插件实现。

**最小验收。** 一个普通插件选择本地资料、生成有来源的上下文，或将结果导出到明确目标；取消后无半写文件，更新插件不删除用户资料。未支持附件时明确返回不支持，不把附件偷偷变成文本路径或声称已上传。

### 14. 客户端更新后，插件能解释哪些功能还可用——贯穿 P0/P1

**证据与边界。** Adapter 已有兼容探针、独立 navigation 可用性、能力撤下与诊断；Windows 有实机证据，macOS 原生客户端和视觉验收尚有待补项。已有机制应延伸到新通道，不另造“全部正常”布尔标志。

**所需分工。** Core 维护通用能力/资源状态和 ABI 兼容，不认识客户端 build 的语义。Adapter 分别报告接入、HTTP/SSE/WS、任务作用域、取消和业务事件映射支持情况。插件用能力探测决定 UI 和降级，保留配置并解释限制；平台专用处理留在相应层。

**最小验收。** 构建漂移只撤下确实失效的能力，不转接独立后端、不偷偷改全局配置；旧插件仍可使用原有 API。Windows/macOS 各有独立记录，fixture、编译通过和真实客户端通过分别标注。

## 最值得先验证的五个用户故事

以下是用于验收基础能力的最小示例插件，不要求本轮交付完整路由或恢复产品。

| 顺序 | 用户故事 | 必须可观察的成功条件 |
| --- | --- | --- |
| 1 | “我给两个任务选择不同 API，客户端无论使用 HTTP 流还是 WS 都能接入。” | HTTP(S)/SSE 与 WS/WSS 各有真实往返证据；两个上游分别收到正确请求/消息；任务与实际落点能关联；无全局配置写入；未覆盖任务明确可见 |
| 2 | “服务 A 在输出前返回错误，我写的插件选择服务 B。” | A/B 的尝试都由插件显式发起并可追踪；下游得到 B 的真实结果；Core 没有隐藏重试；源认证不交叉；插件不选择 B 时原错误可完整保留 |
| 3 | “模型输出了工具调用后断线，我要保留任务并知道还能怎么继续。” | 可看到已交付流和已知 item 状态；失败/未知保持真实；不自动再次执行工具、不伪造完成；需要新的继续动作时有明确入口 |
| 4 | “请求很慢，我点停止，然后重载插件继续使用。” | 取消从客户端传到受管流；资源有确定结束结果；没有迟到请求和占用旧端口；新代不接受旧句柄；原任务历史仍可读取 |
| 5 | “我在两个窗口修改路由设置，并排查一次失败。” | 配置版本冲突可见；已接受请求使用固定快照；新的请求使用明确版本；状态栏/诊断通过公开 API 协作；导出不带正文和凭据 |

第三个故事的首轮成功标准是“失败可解释、恢复不重复副作用”。只有后续针对特定协议、客户端和工具链的实验证明支持续传/恢复，才提高为自动继续。它不是给 Core 安装一个默认恢复算法。

## 建议的短中长期顺序

**短期：证明客户端两种传输均可被插件可靠控制。** 本次完成 HTTP(S)/SSE 与 WS/WSS 基础通道及 Adapter 统一接入，把作用域、生效时机、字节流/双向消息背压、一次性决策、取消/清理、跨源认证和最小诊断一起验收。先用单一写入 owner，多插件链、全局默认和自动恢复按后续具体需求增补。首轮 API 对旧功能保持兼容，真实客户端验收只对已接入路径作结论。

**中期：让第二个、第三个插件不用重复造基础设施。** 提供最小配置存储/版本更新、凭据引用、跨插件订阅约定、少量任务 UI 插槽和开发诊断；由独立的路由示例与另一类插件（例如任务看板或资料连接器）复用验证。按真实需要补任务级操作及附件，继续把 Codex 私有字段留在官方 Adapter。完善 macOS 实机证据，同时维持 Windows 既有功能。

**长期：由具体需求驱动恢复和持续作业。** 在本次 HTTP(S)/SSE 与 WS/WSS 基础上，独立评估业务会话续传、多级处理链、大对象/文件通道、持久调度。Core 只增加通用机制及资源保证；协议转换、智能选路、跨供应商自动恢复、费用/预算、自动工具政策始终可由普通插件提供。没有真实消费者前，不建设全功能工作流引擎、供应商数据库或独立插件市场。

## 仍需验证的事实

- 当前真实客户端哪些新建/恢复入口接受临时 provider 配置？已加载任务是否需要原生恢复，何时开始影响下一请求？以 Adapter 源码及实机证据为准。
- 官方登录/API key 模式分别有哪些请求能够显式接入？未覆盖的内部请求不能依据“模型 API 已接入”推断覆盖。
- 能否从同一 Desktop 连接可靠关联网络请求、turn、item 和工具副作用？无法关联的阶段应怎样向插件报告未知？
- 哪些协议可在收到部分内容后继续？哪些只能由用户发起新的回合？这是未来协议/恢复插件的验证，不是 Core 保证。
- 配置和凭据在插件更新、换源、卸载及重新安装时的保留规则，需要由通用存储契约明确，不能靠插件 ID 或目录名猜测。

这些问题并不阻止本次 HTTP(S)/SSE 与 WS/WSS 通用通道的开发；它们决定插件能向用户承诺多大范围的“切换”和“继续”。
