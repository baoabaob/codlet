# 内存深查与 GUI 监听器修复 · 2026-09-22

**查出并修复了一个真实的 GUI 重载泄漏：SDK 中 React 留在 `document` 上的 `selectionchange` 监听器，使已卸载的旧界面仍然存活。30 分钟空闲没有发现明显泄漏，但反复创建 Chromium 隔离环境的累积仍然存在。**

本轮基线为 Core `f6a7c36`，官方插件为 `fea9796`。环境：Windows 11 x64、Codex 26.915.4065.0、Chrome 153.0.8010.48、V8 15.3.76.12、Node 24.21.0。使用同一处已排除 Defender 的 release 实验运行器目录；未改防护配置、未替换已安装的 MSI、未打包发布。

## 前台 GUI 的真实泄漏

快速连续重载时，GUI 会暂时返回原生页面，稳定后才恢复。此前仅比较后台批次的结果，不能覆盖每次真正显示 GUI 的完整生命周期。本轮补充了逐轮打开界面、确认挂载后再 GC 的测试。

| 指标 | 修复前：2 次前台重载 | 修复后：20 次前台重载 |
|---|---:|---:|
| 回收后 JS 堆累计增量 | 10.21 MiB | 13.52 MiB |
| 每轮观测均值 | 5.11 MiB | 0.68 MiB |
| DOM 节点累计增量 | 386 | 2 |
| 事件监听器累计增量 | 892 | 0 |

修复前每轮增加 **193 个节点、446 个监听器**。通过 CDP 检查已退役 GUI 的隔离环境，发现仍有一个 `document.selectionchange` 监听器；只移除该旧监听器并 GC，节点和监听器分别减少 **193、446**，JS 堆从 550.81 降至 546.36 MiB。这是活体引用的定位与释放对照，没有把未取得的完整堆快照当作证据。

修复位于 Core 提供的 UI SDK：构建时只为自带 React 的文档监听器登记所有权，最后一个 UI owner 退出时移除监听器并恢复其私有标记，使同一 SDK 再次打开页面时能重新注册。没有修改客户端的 React 或全局事件注册方法，也没有复用不同插件代次的隔离环境。

实测中，修复版每个检查点均有真正显示的 GUI、3 个 UI 容器及 1 个样式节点。第 0–15 次节点数都是 1,166，后续为 1,168；监听器通常为 1,624，仅第 2、4 次短暂为 1,628，随后回到基线。抽查第 1、10、20 代，文档/窗口监听器均为 0；当前第 21 代保留正常的键盘、可见性和选区监听器。旧 ABI 闭包中的运行时引用确认为 `null`，检查本身没有增加主窗口的 context 数量。搜索、筛选和 Escape 清空也在实机上验证通过。

前后测试轮数、进程启动阶段不同，表中展示各自的实际增量和观测均值，不把它换算为整台客户端的内存节省百分比。修复后的完整曲线仍有波动：

| 前台重载次数 | 回收后的 JS 堆 |
|---|---:|
| 0 | 263.26 MiB |
| 5 | 272.56 MiB |
| 10 | 269.18 MiB |
| 15 | 272.18 MiB |
| 20 | 276.79 MiB |

第 10–20 次仍增加 **7.61 MiB**，平均 **0.76 MiB/轮**。主要 GUI 对象泄漏已修复，不能因此宣称所有累积都消失。

## 仍然存在的隔离环境累积

| 对照工作负载 | 回收后 JS 增量 | 节点 / 监听器变化 |
|---|---:|---:|
| GUI 后台重载，第 50–400 次 | 140.43 MiB，约 0.40 MiB/轮 | 0 / 0 |
| 空插件重载 200 次 | 68.83 MiB，约 0.34 MiB/轮 | 0 / 0 |
| 桌面适配器重载 100 次 | 0.25 MiB | 0 / 0 |
| UI 适配器重载 100 次，连带 GUI | 49.26 MiB | 页面切换后增加，50–100 次未继续增加 |
| 直接创建 100 个空 Chromium world | 单目标约 15.80 MiB | 未运行插件代码 |

GUI 后台测试在每批检查点没有挂载界面，不能替代上面的前台结果。它证明了另一类累积：每轮为两个目标各创建一个隔离环境；空插件也有相同的 context 数量增长。桌面适配器运行于 main world，未出现相同增长曲线。修复版 20 轮中 context 总数仍从 10 增至 50。

当前浏览器对应的 Chromium 源码中，`WindowProxyManager` 持有 `isolated_worlds_`，每个 `WindowProxy` 又跟踪 global proxy；移除注入脚本不等于销毁这个执行环境。来源：[WindowProxyManager](https://raw.githubusercontent.com/chromium/chromium/199a3a541d76237379e353b348e64045584db057/third_party/blink/renderer/bindings/core/v8/window_proxy_manager.cc)、[WindowProxy](https://raw.githubusercontent.com/chromium/chromium/199a3a541d76237379e353b348e64045584db057/third_party/blink/renderer/bindings/core/v8/window_proxy.cc)、[Inspector Page](https://raw.githubusercontent.com/chromium/chromium/199a3a541d76237379e353b348e64045584db057/third_party/blink/renderer/core/inspector/inspector_page_agent.cc)。

因此，普通使用的剩余风险较低；开发时长时间高频热重载仍会累积，需要后续处理执行环境生命周期。当前应以完整关闭并重新启动 Codlet 客户端作为释放手段。旧版长压力运行中普通 `Page.reload` 没有释放这些 world，总 context 数从 1,514 到 1,516，JS 堆反而从 549.56 到 764.53 MiB；该特定实验不作为修复版页面刷新的普遍结论。

后续架构工作需要同时验收环境可回收、旧代次授权不可恢复、DOM/官方组件兼容、页面导航和辅助窗口的生命周期。不能仅重用 world 名称来隐藏计数增长。剩余堆增量包含环境、相关运行时对象及客户端缓存，本轮没有把每个字节都精确归因。
