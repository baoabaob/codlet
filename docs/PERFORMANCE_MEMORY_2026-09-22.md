# Codlet 真实客户端内存复测 · 2026-09-22

**结论：正常启用的开销是几十 MiB；GUI 反复重载确实有内存累积。已修复其中的 UI 调度器与引用清理问题，40 次重载后的保留 JS 堆增量从 66.17 MiB 降至 16.81 MiB，减少 74.6%。仍有随隔离代数增长的残留，不能称为“完全没有泄漏”。**

这份报告补全并修正 [9 月 21 日报告](PERFORMANCE_2026-09-21.md) 的原生测量空缺。此前 jsdom 没有运行真实浏览器的 MessageChannel 调度分支，因此未发现这次复现的问题。先前的合成测试结果不能替代本次真实客户端结果。

## 正常使用时占多少内存

同一个隔离测试客户端，依次关闭三个官方插件、启用两个 Adapter、启用 GUI、打开 GUI。每个阶段丢弃最初 15 秒，取后续进程采样中位数。打开 GUI 阶段持续 256 秒。

| 状态 | Core 工作集 | Core 私有工作集 | Core 私有提交量 | 客户端私有工作集 | 客户端私有提交量 |
|---|---:|---:|---:|---:|---:|
| 三个官方插件关闭 | 23.11 MiB | 4.62 MiB | 6.15 MiB | 978.83 MiB | 1189.61 MiB |
| 两个 Adapter 启用 | 24.71 MiB | 5.07 MiB | 6.71 MiB | 980.97 MiB | 1191.29 MiB |
| 三个插件启用，GUI 未打开 | 26.09 MiB | 6.25 MiB | 8.22 MiB | 992.76 MiB | 1206.20 MiB |
| 三个插件启用，GUI 打开 | **26.33 MiB** | **6.41 MiB** | **8.36 MiB** | **999.02 MiB** | **1226.31 MiB** |

- 打开 GUI 后，客户端私有工作集相对关闭插件时净增 **20.19 MiB**；再计入 Core 的私有工作集约为 **26.61 MiB**。这是同次运行的净差，包含页面切换与官方客户端本身的波动，不是逐个插件独占内存的精确分摊。
- Core 打开 GUI 时的工作集范围为 25.41–26.46 MiB，私有提交量 7.07–8.54 MiB；本次没有出现 Core 进程 GiB 级增长。
- “客户端”列包含 Electron 主进程、渲染器、GPU 等；不包含 Core、实验协调器、采样插件的 Node 进程或官方 app-server。后者单独记录在数据文件中，不能算成 Codlet 插件开销。
- 关闭官方插件时客户端已接近 1 GiB 私有驻留内存。这次结果不支持把客户端全部 GiB 级占用归因于 Codlet；也不能据此解释不同历史会话和第三方插件下的任意占用。

## 反复重载：发现了什么

旧版和修复版均使用真实 Chromium 客户端、相同三个插件与实验配置。GUI 打开后通过 CLI 顺序重载，每次都核验运行中 Core 返回的 `completed / applied` 回执。每个比较点都对同样的三个页面目标执行 GC，再读取 JS 堆；不是单看任务管理器瞬间数字。

| GUI 阶段 | 修复前保留 JS 堆 | 修复后保留 JS 堆 |
|---|---:|---:|
| 开始重载前 | 262.31 MiB | 265.91 MiB |
| 重载 20 次 | 294.54 MiB | 271.79 MiB |
| 重载 40 次 | 328.48 MiB | 282.72 MiB |
| 前 40 次净增 | **66.17 MiB** | **16.81 MiB** |
| 第 20–40 次净增 | 33.94 MiB | 10.93 MiB |
| 追加至 60 次 | 未测 | 291.56 MiB |

相应的客户端私有工作集，从重载前到 40 次后，中位数增量由 **104.88 MiB** 降至 **35.61 MiB**。这个数字包含分配器保留页、代码和缓存等，不能与 JS 堆增量混用。

修复前，第 20→40 次重载，页面 DOM 节点由 1351 增至 1391，事件监听由 1889 增至 1929。修复后，第 20、40、60 次均为 **1312 个节点、1845 个监听**，不再按代积累这类对象。起点与首次重载后的节点数不同，不能据此声称所有节点均回到了初始页面；这里比较的是后续重复操作的增长。

## 原因与修复

1. UI SDK 内置 React 调度器在初始化时创建 MessageChannel。模块卸载时没有关闭它，旧回调仍保留模块对象。现在用 SDK 内部的词法构造器记录这些通道，退休时清空两端回调并关闭端口。**没有替换页面全局 MessageChannel，也没有关闭官方客户端自己的通道。**
2. 退休的隔离环境仍能保留不可变的运行时入口。现在按需加载 UI，最后一个使用者退出后释放 UI 工厂、i18n、服务工厂及清理函数引用；退休的生产环境拒绝再次激活。
3. 大型 SDK 和小型运行时分成两个注入脚本，避免只为保留运行时入口而同时保留整个 SDK 源码。两个脚本由同一插件代管理，部分安装失败、导航和卸载均清理两者。
4. Core 自身的事件循环唤醒通道也会先清空 `onmessage`，再关闭端口。

保留每代不同的隔离环境及授权身份，没有通过复用旧环境掩盖增长。

## 剩余问题与 Adapter 结果

GUI 第 40→60 次仍增加 **8.84 MiB**；全部停用后堆为 284.34 MiB，没有回到初始基线。因此这次提交是显著降低累积，**不是彻底解决反复热重载的全部保留成本**。

另做空环境对照：在同两个目标中分别创建 20 个不加载插件的隔离环境，共 40 个。GC 后仍净增 **6.78 MiB**。这支持“剩余增长有相当部分来自隔离环境本身”的判断，但不能证明所有剩余对象的引用来源。一次完整堆快照尝试因原始 CDP 事件订阅溢出失败；没有把失败快照或其造成的工作集峰值作为泄漏证据。

GUI 停用后，两个官方 Adapter 分别追加真实重载测试：

| 插件 | 重载次数 | GC 后 JS 堆增量 | 节点 / 监听变化 |
|---|---:|---:|---|
| Desktop Adapter | 20 | +0.006 MiB | 1296 / 1836 → 1296 / 1836 |
| UI Adapter | 20 | +0.037 MiB | 1296 / 1836 → 1296 / 1836 |

这两个工作负载没有出现类似 GUI 的持续大量保留。上述很小的差异仅代表本次测量结果，不应外推为所有插件、所有长期使用场景的保证。

后续需要单独处理高频热重载后的隔离环境保留，并补充长时间真实会话与 macOS 测量；当前仍不应把“无泄漏”作为验收结论。

## 环境、计数口径与验证

- Windows 11 x64 Build 26200，i7-12700K，20 个逻辑处理器，约 32 GB 内存；官方客户端 26.915.4065.0。
- Core 优化前 `ab2f61f`，优化后为本报告所在提交的代码；release 构建，产品版本仍为 `0.2.0-preview.4`。官方插件 `e48b64e`：Desktop Adapter 0.1.0、UI Adapter 0.1.1、GUI 0.1.1。固定 Node v24.21.0。
- Windows 进程计数使用 `PROCESS_MEMORY_COUNTERS_EX2`：工作集是全部驻留页，私有工作集是私有驻留页，私有提交量包含可能不驻留的已提交页。单位 MiB = 1,048,576 字节；JS 堆是另一种口径。字段定义见 [Microsoft 文档](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2)。
- 原生采样约每 1.2 秒一次，按 PID 和创建时间核验进程；Chromium 指标每 5 秒一次。GUI 列表中有额外一行临时采样插件，其独立 Node 进程已排除。所有 GC 和诊断只针对自己的隔离测试客户端。
- 用户已自行增加 Defender 排除项。本次没有更改防护设置。测试完成后关闭了本次实验客户端，原实验插件配置按备份逐字节恢复，用户原客户端继续运行。
- 通过 **88 项相关回归**：JS 生命周期/UI 33 项、真实 Node VM 的 CDP/重载等 Rust 用例 40 项、渲染器单元测试 15 项。新增回归覆盖真实 MessageChannel 调度分支、原生通道不受影响、弱引用可回收和退休代不可复活。release Core 与实验运行器构建成功；重载后实际 GUI 仍可显示并返回原生新会话页面。
- 仅更新源码及实验运行器；**没有替换用户已安装的 Preview 4，也没有生成新 MSI。**
