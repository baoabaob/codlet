# 可销毁 Renderer 容器实机实验 · 2026-09-22

**固定页面桥接层 + 可销毁 Worker 的路线在原型中成立：800 次完整创建、官方控件挂载、事件往返、销毁之后，受测页面的 JS 堆累计增加 0.507 MiB，隔离环境、DOM 和监听器数量均不增长。尚未将正式插件运行时或 Codlet GUI 迁移到这套模型。**

后续架构复审：用户要求评估能力等价性与长期冗余后，已暂缓本页“能验收什么，下一步做什么”中的公开 Worker 实施设想，改为优先评估复用 Host 和完整自有 UI 视图。以下实验数据仍有效；当前设计建议见[插件执行与回收架构权衡](PLUGIN_EXECUTION_ARCHITECTURE_2026-09-22.md)。

实验基于 Core `3acf85c`、官方插件 `fea9796`，Windows x64 官方桌面包 `26.915.4065.0`、Chromium `153.0.8010.48`、V8 `15.3.76.12`。使用原来已排除 Defender 的测试运行器，未修改防护设置、系统信任、用户原客户端或安装包。此轮没有 macOS 实机结果。

## Worker 的结果

同一固定桥接 world 只初始化一次 UI SDK。每轮创建一个 Dedicated Worker；Worker 持有并按页写入 8 MiB 数组，通过结构化消息请求桥接层挂载实际 SDK 的 Button、Input、Switch。程序触发按钮，Worker 回复成功之后，桥接层撤销该实例、终止 Worker、卸载界面。每 50 轮执行 GC 并记录两个不同 V8 isolate 的指标；没有把同一 isolate 重复相加。

| 同一桥接层的累计循环数 | 两个受测 renderer 的 GC 后 JS 堆 | context 数量 | DOM 节点 | 监听器 |
|---|---:|---:|---:|---:|
| 0（10 轮预热后） | 256.059 MiB | 4 + 3 | 918 + 138 | 1,075 + 457 |
| 200 | 256.370 MiB | 4 + 3 | 918 + 138 | 1,075 + 457 |
| 400 | 256.467 MiB | 4 + 3 | 918 + 138 | 1,075 + 457 |
| 600 | 256.557 MiB | 4 + 3 | 918 + 138 | 1,075 + 457 |
| 800 | 256.567 MiB | 4 + 3 | 918 + 138 | 1,075 + 457 |

前 400 轮增加 **0.407 MiB**，后 400 轮增加 **0.100 MiB**。每个回收检查点的 Worker target、实验 UI 容器和活跃实验 owner 都为 0。8 MiB 是每个活跃 Worker 的分配量，不能把 800 轮的累计分配量解释为同时驻留内存。

页面堆统计不覆盖 Worker 的独立堆和全部原生分配，因此另采样了自有进程的私有工作集和私有提交量：

| 指标（稳定区间中位数） | 开始 | 第 400 轮后 | 第 800 轮后 |
|---|---:|---:|---:|
| 桌面相关进程私有工作集 | 996.96 MiB | 1,019.40 MiB | 1,019.20 MiB |
| 桌面相关进程私有提交量 | 1,221.82 MiB | 1,244.13 MiB | 1,241.95 MiB |
| Core 私有工作集 | 5.414 MiB | 5.430 MiB | 5.465 MiB |
| Core 私有提交量 | 7.738 MiB | 7.738 MiB | 7.742 MiB |

桌面私有工作集在这两组中的采样峰值分别为 1,080.63 / 1,086.14 MiB。首组之后保留约 22 MiB 的额外驻留，第二组没有继续同幅累积；这里没有声称所有内存都精确回到初值，也没有把全部额外驻留归因到某个分配器。表中排除官方后端和探针/协调器 Node 进程；Core 单列，不能与不同内存口径混加。起始取检查点前 8 秒，结束取检查点后 8 秒，各 6–7 个样本。第二组采用第一组结束后的稳定样本作为原生内存基线，避免误用第一组仍在执行时的高水位。

之后修改测试工具以增加 iframe 对照与撤销验证，再用最终探针进行另外 **400 轮** Worker/UI 复验：堆增加 **0.341 MiB**，context、DOM、监听器仍不增长。它与前 800 轮之间有实验桥重新安装及 iframe 压力负载，分别报告，不拼成一条从 0 开始的 1,200 轮曲线。

## iframe 对照和代次隔离

| 受控实验 | 次数 | context 增量 | GC 后 JS 堆增量 | 判定 |
|---|---:|---:|---:|---|
| 当前主页面每次创建新的空 isolated world | 100 | +100 | +16.529 MiB | 复现原生环境累积 |
| iframe 每次新 world，直接操作父页面 DOM，再移除 iframe | 100 | +100 | +19.291 MiB | 移除子 frame 不会清掉留在父页面的 world |
| sandbox iframe 每次新 world，尝试访问父页面（被拒绝） | 200 | +200 | +33.055 MiB | 仅尝试取父窗口也能在该配置下留下父页面 world |
| sandbox iframe 默认 world，父页面访问被拒绝 | 200 | 0 | +1.801 MiB | 可销毁容器，但没有直接父 DOM 能力 |
| sandbox iframe 每次新 isolated world，完全不取父窗口 | 200 | 0 | -0.131 MiB | 子 frame 执行环境能被回收 |
| iframe 复用同一个 named world，直接操作父 DOM | 200 | +1（一次初始化） | +0.217 MiB | 内存有界，但下面的代次隔离测试失败 |

复用 named world 的攻击性对照只使用实验函数，没有使用真实 Core 权限：旧 iframe 在父窗口保存一个旧闭包，移除旧 iframe、创建新 iframe 后，旧闭包仍能经父 DOM 取得并调用新实例的测试函数，结果为 `borrowedNewCapability: true`。因此不能为了压低内存，直接把生产中的每代独立 world 改成共享名称。该结果指向**被测试的替代架构缺陷**，不表示现有生产隔离已被绕过。

Worker 对照先确认存活实例确实发送心跳（收到 31 条），然后撤销并终止实例。退出后没有继续接受心跳；保留的旧接收回调即使伪造新代次编号也被拒绝，旧 UI 没有重新挂载。检查同时包括 owner 身份和代次，不能只信任消息里的 `generation`。

这些对照缩小了原因：iframe 本身可以回收，但让每代新的 world 进入长寿命父页面，会再次引入保留。仅复用 world 虽然解决数量增长，却无法提供本项目要求的代次边界。

## 能验收什么，下一步做什么

此次可以验收：可销毁执行容器的基本可行性、固定桥上实际官方控件的反复挂载/卸载、按钮消息往返、基础代次撤销，以及数百轮下环境数量有界。按钮事件由程序触发，UI 放在实验区域；不是完整 GUI 的原生鼠标、键盘和视觉验收。

正式实现需要保留现有插件功能，按以下顺序推进：

1. Core 增加独立、可选择的 Worker 执行模式。一个目标只有固定桥，插件业务代码进入可销毁 Worker；主进程掌握实例、代次、撤权、超时、崩溃和目标关闭的生命周期。插件不能取得桥本身或别人的消息端口。
2. 为消息、并发和队列设置硬上限；消息到 Core 的身份由拥有者绑定，不能相信插件自报。处理旧消息、异步结果晚到、取消、导航和辅助窗口。Worker 本身不是完整权限沙箱，浏览器网络/存储能力还需要明确能力模型。
3. Adapter 和 UI SDK 提供受控页面/组件协议。复杂 UI 的门户、模态框、焦点、i18n、主题和页面路由需要逐项迁移并验收。此原型只有固定的三种控件，不能冒充已经实现任意 React 组件的跨 Worker 渲染。
4. 先迁移官方 GUI；现有直接操作 DOM、依赖同步页面对象或 main-world 的插件继续走原有路径，直到有功能等价的替代能力。不得通过静默改执行世界来破坏插件。之后再做 Windows/macOS 实机、真实 GUI 反复重载、长对话和故障注入测试。

因此本轮不把“累计问题已全部修复”写入生产状态；它给出了经过实测的重构方向，并排除了两种看似简单但不满足要求的替代方法。

## 复现、数据和清理

实验代码是 [scripts/renderer-container-probe.cjs](../scripts/renderer-container-probe.cjs)，仅供已拥有的隔离 Lab 使用，不由产品启动器加载。开发者可在实验 Host 插件中以 `require(probePath)(ctx, outputDirectory, coreRepository)` 创建探针；该插件需要显式的 `host.process`、`cdp.raw` 授权。`run({id, action, count, ui, mode})` 支持 `checkpoint`、`worker`、`frames`、`worlds`、`revocation`、`shared-frame-revocation`、`close`。UI 源码取所提供 Core 仓库的 `bundled/runtime/ui.js`。每个案例使用唯一 ID，先预热和记录独立基线，再运行有界批次。必须在权限仍有效时先 `close`/`dispose`，再关闭实验 Host；不要连接用户正在使用的客户端。

本机驱动、原始 JSONL、原生采样、CLI 回执和失败的准备记录保留在 `.codlet-artifacts/renderer-containers-2026-09-22/`。其中：

- 首次冒烟采用浏览器定时轮询，受后台节流影响；正式 800 轮改为等待 Worker 消息，不混入首次冒烟耗时。
- 开发中一次探针重载时，已退役的 `cdp.raw` 无法再执行实验桥清理；随后在有效授权下显式关闭旧桥。正式产品需要 Core 持有容器清理权。
- 默认 frame 的首次冒烟被大量旧 context 的事件重放影响；测试工具改为先 `Runtime.enable`、再订阅新 frame 事件，之后 200 轮成功。保留失败记录，没有把失败冒烟算进通过批次。
- 桥重新安装之间的基线有变化；每组分别取基线。连续 iframe 场景的原生采样窗口可能跨到下一组，因此不发布它们作为严格原生内存 A/B。
- 原子配置恢复前检查没有额外修改。最终实验入口、桌面、Core、后端、采样器全部退出；测试注册表按字节恢复，原客户端/后端 PID、创建时间和映像路径保持一致。
