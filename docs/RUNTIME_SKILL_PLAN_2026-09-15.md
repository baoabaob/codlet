# Codlet 运行时技能

2026-09-15：已实现 Core 提供的 `codlet` skill，正常启动即注册，不依赖管理 GUI 或可选适配层插件。当前 Native 接入验证范围为应用 `26.908.40834` / build `8881`，App Server `0.154.0-alpha.6.2`。

## 生命周期与目录

Core 将内嵌技能、按需参考和公开类型释放到 `Codlet/runtime-skills/codlet/`，同一注册表由独占锁保护。官方 `skills/extraRoots/set` 只登记进程内搜索路径，不修改用户或项目技能目录，也不保存官方配置。Core 退出时撤回自己的目录并清理资源；安全模式不创建技能资源或注册接口。旧的随机目录仅在确认由同一注册表生成后清理。

默认插件目录为当前注册表目录下的 `packages`，新插件使用用户确认的名字/ID 作为子目录，远端托管包继续使用 `packages/github`。目录不会自动授信或加载；技能通过带本次运行参数的 CLI 包装脚本预览、授权、注册和启用。

## 官方接口与共存

Native 接入复用现有本地 App Server 请求客户端，不建立第二个 Desktop app-host 连接。对 `skills/extraRoots/set` 的本次 Core 窗口调用通过 Core 串行租约合并；保留官方请求的其它根目录，再追加自己的唯一目录。窗口、默认执行上下文和租约票据绑定；旧窗口不能完成另一个窗口的注册。连接重新初始化时，下一次技能列表/任务请求会重新登记已知目录。

本机构建的完整 JavaScript 资源检索只在方法分组表发现 `skills/extraRoots/set`，没有独立的 Native 初始化写入者。Core 从自己新启动的后端开始维护目录集合；普通官方客户端不注入此桥接。该协议没有读取原始 extraRoots 列表的 getter，因此不支持把桥接附加到任意已运行、目录所有权未知的后台进程。

“创建插件”打开可编辑的新会话草稿，内容仅为 `/codlet 帮我创建一个插件：`，不会自动发送。当用户实际提交以 `/codlet` 开头的消息时，桥接补上官方 `skill` 输入项；已经有该 skill 项时不重复添加。普通消息不增加技能输入。

## 技能内容与验收

缺少的信息才询问：需求、插件名、默认/自定义目录、是否使用官方 UI（默认不使用）。功能确定后读取真实插件清单，说明推荐依赖的用途和原因，允许不依赖；需要客户端集成时优先推荐官方适配层。随后用简单语言解释运行层级和必要权限，用户确认后实现。组件、样式和完整类型按需阅读。

Core 测试覆盖多窗口竞争、保留其他根目录、旧上下文票据拒绝和资源清理。桥接测试覆盖无 GUI 的原生连接、显式 skill 输入、普通消息、重新连接及撤回。实际 Dev 的 `skills/list` 返回唯一 `codlet`、共 37 个技能、无错误；管理 GUI 停用时结果保持一致。技能 CLI 返回真实插件清单，技能格式校验通过。

证据位于 `.codlet-artifacts/runtime-skill-2026-09-15/`；`live-skill-normal.json` 与 `live-skill-gui-disabled.json` 可比对。旧任务已经收到的技能上下文属于历史，运行时卸载不会抹去它。
