# 下一阶段计划：插件 UI、Desktop Adapter、导入与跨平台

状态：2026-09-11 产品方向与建议开发顺序。基线为 M3/M4 开发候选 `01a4009`。下文列出的新增接口、GitHub 导入及非 Windows 移植尚未实现。

## 已确认的产品方向

Codlet 继续定位为依托官方客户端的轻量插件运行时，沿用现有 capability kernel、registry、权限、RPC、generation 与生命周期 receipt。社区生态的新增工作集中在分发、发现、兼容性说明和维护规则。

Codlet 内置简单的“插件”页面；发现交给 GitHub Topics 与社区目录。当前不建设独立 Codlet Market，也不引入另一套插件管理内核或独立管理器应用。

| 部分 | 职责 |
| --- | --- |
| Codlet | 导入、显示来源/版本/权限/兼容性、启停、重载、移除，以及明确的更新/回退操作 |
| GitHub | 作者维护源码、发布构建好的版本包、保存变更记录、通过统一 Topic 帮助发现 |
| 社区目录 | 插件介绍、分类、推荐、维护状态和导入入口；可以只是 Markdown 或静态网页 |

目录中的推荐与来源信息不代表执行授权。来自任何入口的同一插件都经过相同的本地检查和生命周期流程。

## M3.1：UI renderer 与 UI Adapter

这一轮把已有 GUI 中可复用的行为变成插件作者能使用的接口。

| 层 | 首批扩展 | 验证重点 |
| --- | --- | --- |
| 通用 renderer UI helpers | 按钮、开关、设置行、确认框、加载/错误状态；事件、焦点、快捷键注销与资源清理 | 普通 DOM 事件本地处理；卸载后没有 listener、observer、timer 或样式残留 |
| 可选 UI Adapter | 版本化外观角色、设置 surface，以及经过实机确认的菜单/侧栏/状态区挂载位置 | 私有 selector、主题字段和平台布局差异集中维护；缺失位置能明确报告 |
| 消费者插件 | 内容、配置、业务动作与显示 | 管理 GUI 与一个普通 UI 插件复用同一接口，权限独立于控件外观 |
| 后续展示扩展 | 消息旁操作、折叠、标注等 presentation transform | 显示变化与已保存 Thread/Turn/Item 历史分开说明 |

首批只选管理页和示例实际需要的少量角色/挂载位置；接口名在验证后冻结。若某个宿主位置没有稳定、可诊断的结构，就不提前承诺支持。组件逻辑不依赖宿主 React/Radix 私有注册，跨 world 不传递 DOM/React 对象。

实机检查包括明暗主题、字体/缩放、窄窗口、键盘与焦点、宿主重建、插件重载与多窗口。现有详细设计继续作为依据：[UI Adapter 能力提案](UI_ADAPTER_CAPABILITIES.md)。

## M4.1：Desktop Adapter

| 优先级 | 扩展 | 条件 |
| --- | --- | --- |
| 首批 | 读取当前选中任务/回合及其变化；定位、打开、恢复任务 | 沿用实际 Desktop 连接和 UI 状态，保留 thread/turn/item 标识和 owner/follower 区别 |
| 首批 | 拦截器管理与诊断：来源、顺序、耗时、失败原因、当前是否可用 | 继续在实际提交前运行，卸载/超时后不能恢复迟到提交 |
| 后续 | 任务创建、附件/更丰富输入、模型及技能选择、更多已验证的 server-request | 每项独立核对 schema、授权、事件与 UI 往返后再公开 |
| 持续维护 | 更细的 capability 可用性、构建兼容说明、已知降级路径 | 某项失效只撤下对应能力；保持当前连接，不改用独立后端 |

当前 v1 的“已加载 local owner 任务、文本输入”限制在这些能力交付前仍有效。展示变换属于 renderer；修改后端权威历史不随展示扩展自动获得支持。上述业务映射继续留在可选 Adapter，Core 不增加 Codex 私有方法或模型字段。

## M5a / M5b：导入和管理方案

“插件”页面保留三个直接入口：

1. **从本地文件夹导入**：选取已有 `codlet.json` 目录，检查入口、权限与依赖，展示预览后注册。开发目录继续引用原路径，明确是否启用 watch。
2. **从 GitHub 链接导入**：解析仓库或 release 链接，选择具体 release 和插件构建资产，展示来源、版本、平台、兼容性与权限，确认后安装至 Codlet 自己管理的目录。
3. **浏览社区插件**：打开 GitHub Topic 或社区目录网页；返回 Codlet 使用同一导入流程。

已安装列表显示来源、版本、运行状态、权限和不可用原因；提供启停、重载、查看权限、撤销、移除，以及对托管安装版本的显式更新/回退。先完善本地导入，再加 GitHub 来源，避免把界面与网络下载一次耦合。

导入服务只负责来源解析、预览、下载、校验和文件落地。注册及后续激活仍交给现有管理机制，GUI 和 CLI 共用操作结果。更新先准备候选，检查权限变化与依赖，再走已有代次替换和补偿流程；已提交操作通过原 receipt 查询，不自动重放。

本地开发目录的“移除”只取消注册并停用，保留作者文件。托管安装目录与插件数据分别记录所有权；清除下载包、删除插件数据必须有明确操作语义。不能因来源换了仓库或插件 ID 相同就静默继承旧来源的信任。

### 发布包与兼容性

发行资产包含构建好的 JS、`codlet.json`、所需资源、许可证和说明；导入时不执行仓库构建脚本或安装脚本。普通仓库源码链接如果没有可识别发布包，应解释原因，并提供手动下载/本地导入途径。

记录所选仓库、release/tag、具体资产及内容摘要。更新时展示版本差异、权限增减、依赖与兼容性变化；用户主动选择更新。内容摘要用于识别下载内容，不能替代对插件作者的信任。

兼容性元数据需要分别描述：

- 插件包版本与兼容的 Codlet SDK/runtime 版本；
- capability API 版本与依赖；
- OS、CPU 架构及所需系统能力；
- 声明兼容的 Codex 构建、实际验证过的构建和已知限制；
- 作者、源码、许可证、反馈入口及维护状态。

这是后续 schema 设计要求，当前 `codlet.json` 不因本文自动接受新字段。新增字段需有向后兼容方案，原有 capability 依赖模型保留。下载器不引入 npm 式依赖解析或静默安装其他插件；缺失依赖需要清楚列出。

GitHub 提供按 release 读取信息和列出资产的 API，可据此解析下载候选；具体版本和资产选择属于 Codlet 的导入规则。[GitHub Releases API](https://docs.github.com/en/rest/releases/releases)

### 社区发现与维护规则

统一发现标签建议使用仓库 Topic `codlet-plugin`；这是待采用的社区约定，未创建或登记专属市场。GitHub 的 Topics 本身用于按主题发现相关仓库；版本发布仍使用 release/tag。[GitHub Topics 文档](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/classifying-your-repository-with-topics)

社区目录的最小条目包括插件名称、简介、分类、作者/仓库、发布入口、权限摘要、支持平台、兼容/已测构建、最近核验日期和维护状态。维护规则包括：

- 作者随版本更新权限、兼容性、变更记录及反馈入口。
- 目录区分“作者声明”“目录实际验证”“未知/失效”，推荐不等于兼容性通过。
- 长期未维护、上游失效或作者移交时更新状态和来源说明，保留可追溯记录。
- 下架/标记问题影响目录推荐，不在用户机器上自动停用或删除已安装插件。
- 社区入口可提供导入链接，也可提供复制即用的 CLI 命令；CLI 和 GUI 使用同一解析与授权流程。

具体 GitHub CLI 导入语法和可选的 `codlet://` 链接协议尚未实现、尚未冻结。第一版优先让用户复制 GitHub release URL 到导入框；CLI 支持交付后再给出可执行安装命令。深链接最多带入一个待预览来源，不能跳过授权或自动执行远程脚本。Codlet 不承担社区账户、评分交易或独立 Market 服务。

## P0 / P1：跨操作系统适配

现在就做 P0，防止新增导入路径、配置存储和 SDK 把 Windows 假设扩散到通用逻辑。完整移植按平台单独交付。

当前代码证据：`src/lib.rs` 中 Host runtime、JS runtime、OS broker、管理 CLI 等模块仍受 `cfg(windows)` 限定；`Cargo.toml` 的系统绑定位于 Windows 依赖；运行时 pin 和打包流程仍面向 Windows。存在某个架构的 Node pin 不等于该架构的 Codlet 已通过验收。

| 可保持共享 | 需要逐平台实现/核验 |
| --- | --- |
| manifest、registry 模型、capability/权限契约、generation/receipt 状态机、JSON RPC、JS API | 官方客户端发现、可验证启动路径、参数及环境继承 |
| 通用导入解析、包元数据与内容校验规则 | 数据目录、路径/链接处理、文件锁、原子替换 |
| renderer helpers 与大部分 Adapter 语义代码 | Host 子进程/进程组、退出与资源回收、authenticated 本地 IPC、对端身份 |
| 共同测试场景和诊断 DTO | Node 产物/许可证、签名、安装升级卸载、平台 UI 差异与 Desktop build 探针 |

先定义最小平台接口，用现有 Windows 行为做第一份实现，保持内核与生命周期语义。非 Windows 平台需要各自的 OS 资源控制办法，不把 Windows Job Object 或 named pipe 当成跨平台保证。仅通过编译不足以宣布支持。

P0 为 Windows x64、Windows arm64、macOS 和 Linux 分别登记 OS/架构、官方客户端可用性、启动机制、测试设备和阻塞项。macOS/Linux 的官方客户端可用性须在开展移植时按官方当时信息核对；本文不提前声明其支持状态。P1 的先后顺序按这些证据和测试条件确定。

P1 从一个目标平台做完整纵切：启动 → Host/renderer → 插件导入/启停 → 当前 Desktop 读写 → 正常退出/故障回收，再扩展到下一个平台。每个平台单独记录 M0/M1 与 Adapter 兼容性门禁，Windows 已有结果不平移为其他平台的通过证明。新增平台不会要求重做插件生态协议或另建管理内核。

## 发布与当前交付的区别

M3/M4 候选已经交付，不代表本文新增功能已实现。M0/M1 重复运行、官方入口纯净性和 Runtime Host crash 等历史门禁继续保留，在发布阶段集中处理；日常改动按影响范围验证，不为每个文档或界面小改动重跑全套。

本轮改动为计划文档；实施状态以各里程碑验收记录为准。
