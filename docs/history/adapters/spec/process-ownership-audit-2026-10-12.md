# 诊断进程归属修正与历史审计

`verify-native-retirement.mjs` 和 `measure-native-baseline.mjs` 的旧算法递归 ParentProcessId，但未比较子/父创建时间。Windows 会复用 PID；旧子进程保留的父 PID 可以碰巧指向新测试进程，从而错误导入整个旧子树。这是诊断归属缺陷，导航公开接口不变。

## 修正

- 根按 PID、完整创建身份和镜像核验；每条子边要求子创建时间不早于该父实例。缺时间或身份漂移明确拒绝，排除的父节点不继续导入其后代。按进程名排除不能解决身份问题，本实现不用名字判断子进程归属。
- `creationTime` 保留 Windows FILETIME 的亚毫秒精度；PID 相同、创建时间只差 100ns 也不是同一实例。
- CIM CreationDate 只有微秒精度，因此先用它预筛，再关联 Get-Process 的完整 StartTime；最后重新按完整时间核验根及每条边。两次读取间消失或换身份的候选记录为 raced；含这种变化的 CPU 基线不能标 stable。
- 新 capture 记录 roots、parentPid、parentCreated、ownership method、rejected edges 和竞态；新 CPU 报告保留所有区间的完整进程快照/CPU/内存，支持逐区间重审。
- closed 拒绝把旧 PID-only capture 继续当作有效归属证据；旧文件不覆盖，使用单独离线审计。退出核验仍只读，不终止任何进程。
- 另外三份既有 opt-in 宿主验证脚本本来已有启动前快照排除和父身份复核，但也缺少子/父时间比较，已加入同一必要条件。这次没有运行其启动或停止逻辑。

最后一份原 closed 报告残留的正是这九个身份。按必要创建时间下限排除后，记录残留为空；**这不等于从缺少父链的旧报告中证明另外 27 个都是测试成员**。排除依据是时间，不是它们的 Steam 名称。七份旧 closed 中四个显式根 PID 均无记录残留；历史捕获身份退出的事实与完整组归属的证明必须分开。

本仓库 `.artifacts` 的 CPU/privateBytes/oneCorePercent JSON 检索只发现 `empty-home-baseline.json` 这一个 OS 组基线。已逐份核对其 coordinator `1791709680234-21436`、25 个最终身份和五个区间：没有成员早于已核验 manager 的 08:54:30 UTC；但只有最后的身份清单和区间合计，没有父链及每区间每进程 CPU/内存。它无法完整重算或证明未污染。原数字保留，**撤回其作为“独占测试进程组 CPU/内存”或 Adapter 增量成本证据的资格**；不猜测一个修正值。

`native-owned-probe-host.cjs` 的 CDP `Performance.getMetrics` 来自精确 owned Target/session，未用这个 ParentProcessId 递归算法。该算法缺陷不改变那些 renderer task/script/layout/style/heap 原样本；它们原有的 hidden/非前台/非 OS CPU 等限制仍保留。Native 导航/组件功能结果也不依赖进程数合计，不能将这次诊断修正扩写为它们的重新验收。

## 验证与未做事项

四项新回归覆盖根 PID 复用、旧子树及更新后代、每层时间顺序、未知日期、亚毫秒差异、乱序输入和名称无关性。相关三组测试总计 **22/22 通过**，修改脚本语法检查通过。只读 Windows smoke 以运行检查脚本自身的 Node 为根，确认完整身份/归属方法；已记录两个采样间自然退出的临时查询子进程为 raced，未将它们误算成稳定组。

没有重新启动测试 profile、代跑消费者、改旧证据或操作 Steam 等非测试进程。分屏会话另行完成其本轮只读纠正核验；本离线审计不借用现在的父 PID 关系给历史成员重新赋归属。
