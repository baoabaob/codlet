# Official traffic Adapter contract

This is the historical traffic contract imported into Core v1. Maintained Native/source mappings and Host helpers now live in Core; ordinary consumers use `context.codex.traffic` and their own broker grants. The named versions and acceptance below retain their original scope. Current behavior is defined by the [Core traffic contract](https://github.com/baoabaob/codlet/blob/main/docs/spec/traffic.md), with no separate Adapter installation.

## Scope and evidence

The reviewed Windows Desktop packages `26.915.4065.0` and `26.917.6896.0`, and Apple Silicon package `26.917.62051`, run Owl main processes. The official Adapter uses a pre-entry hook in one newly owned, identity-checked process. It never edits the installed archive. Their verified `performDesktopFetch` paths reach `ApplicationNetwork.fetch` and the upload-progress `request` branch after the official auth, workspace policy and cancellation decisions. Both paths dispatch through the original `ApplicationNetwork.request`, retaining Electron's Chromium session, cookies, proxy, TLS and cancellation behavior. Core intercepts the initial dispatched request and the final response. Native redirect events identify the actual final URL and synchronously recheck each destination against the official Desktop policy; Core authorizes the final response callback against that URL's origin. Electron does not expose intermediate 302 response bodies to this path, so intermediate responses and redirected request hops cannot be read or rewritten by plugins. A plugin-requested cross-origin rewrite omits ambient session credentials for its whole native redirect chain.

The exact reviewed main, bootstrap and `src` module hashes are checked before their private classes are patched. A changed build disables that source. Desktop coverage is limited to those main-process HTTP/SSE calls. Browser pages, remote/cloud backends, attachments and Realtime/WebRTC have no claimed coverage.

The reviewed local Windows `codex.exe` profiles are `0.155.0-alpha.9.2` (SHA-256 `bc45017e8239dc150258f69309ced9df6bbcdf5b8e4f346decf780ac0999e226`) and `0.155.0-alpha.16` (SHA-256 `97d4d67419d0ac2f71342f9a5e850f9468aa622618de8ea823223edb9a91926a`). The reviewed Apple Silicon `codex` profile is `0.155.0-alpha.16.3` (SHA-256 `c67698d0990aae05211d9c43ab343ad9517e406824dea77eca103a2806232b3a`). Their Responses HTTP/SSE and WebSocket model traffic is routed through Core's private plaintext source endpoint by process-local provider config overrides. This is an explicit endpoint route; it does not hook encrypted sockets in the backend. The original effective model, provider, auth store and environment remain in place. A read-only probe projects only provider base URLs and account type. The exact owned app-server child receives the overrides; unrelated children and normal launches are unchanged. Existing `CODEX_CA_CERTIFICATE` or `SSL_CERT_FILE` is read as bounded PEM and attached to the exact upstream route, alongside normal trust roots. Core pins the old route and trust to active exchanges during an update.

The reviewed backend uses `openai_base_url` for built-in inference, including ChatGPT auth, and `model_providers.<id>.base_url` for custom Responses providers. Its `chatgpt_base_url` setting is a separate backend service endpoint. When a local account update changes API-key versus ChatGPT mode, the Adapter updates the built-in route before later Stdio sends. The verified local Stdio hook also rewrites task-local provider base URLs at `thread/start` and `thread/resume`, covering both renderer and internal requests. If route registration fails, that request receives an error and the original external base URL is never sent. Existing configured provider selection is unchanged when the task supplies no new base URL.

The [request-chain research](request-chain.md) records the installed call sites and controlled six-mode backend experiment. Synthetic tests covered custom, built-in API-key and ChatGPT auth; HTTP, SSE and WS; Zstandard ChatGPT bodies; WS prewarm and continuation; cancellation; and two concurrent task IDs. These fixtures do not establish live login refresh or universal client networking.

The official Apple Silicon [Sparkle appcast](https://persistent.oaistatic.com/codex-app-prod/appcast.xml) lists the versioned, signed ChatGPT `26.917.62051` ZIP (build `10789`). Its ZIP, ASAR, backend and Owl module hashes are recorded in [`mac-plaintext-reviewed.json`](../../../../codex/tests/fixtures/traffic/mac-plaintext-reviewed.json). Controlled native Apple Silicon acceptance ran eight synthetic backend modes, including ChatGPT Zstandard and concurrent two-task HTTP/WS routing with cold resume. Two exact-owned Desktop runs then exercised HTTP and WebSocket model turns alongside main-process fetch, upload progress, same- and cross-origin redirects, final-response authorization, cookie equivalence and cleanup. Both sources activated; the HTTP and WS reports each returned `accepted: true` with no owned processes left. This establishes the named local source paths for that exact build, not live OAuth, native GUI navigation, installer UX or other network surfaces.

## Host registration SDK

Bundle `host/codex-traffic.cjs` into the consuming plugin's Host entry and call `createCodexTraffic(context, compatibility)`. Registrations use that plugin's own `context.traffic` grants. Exact origins, `traffic.intercept`, and any plugin-requested `traffic.redirect` destination grant remain Core decisions. `traffic.sensitiveHeaders` is required before a callback can see `x-client-request-id`; otherwise `context.codex.threadId` is null. On the verified backend's Responses HTTP requests and WS handshakes, a single well-formed value maps to the task ID; ambiguous or missing values stay null. The Adapter does not lend its own launch authority to consumers.

```js
const { createCodexTraffic } = require('./codex-traffic.cjs');
exports.activate = async context => {
  const api = createCodexTraffic(context, verifiedBackendIdentity);
  const handle = await api.registerInterceptor({ id: 'responses', kinds: ['model.responses'], origins: ['https://api.openai.com'] }, {
    request(request, { codex, signal }) {
      // undefined leaves this one-shot request stream unchanged.
    }
  });
  // Await handle.setEnabled(false), handle.close() or handle.dispose().
};
```

The SDK filters `model.responses` and `model.list` paths within the declared origins. It explicitly decodes bounded JSON for identity, gzip, deflate, Brotli and Zstandard, and removes stale content length/encoding/digest headers on a rewrite. SSE byte chunks are not assumed to be whole events. The SDK does not replay non-idempotent requests or move server-owned WS continuation state between providers. `probe().available` requires both the reviewed backend build and Native's `owned-backend-provider` activation; Desktop-only activation is insufficient.

The renderer `codex.backend.write@1` / `registerThreadConfiguration` callback changes task-local model/provider configuration at thread start/resume, and can select a model for each `turn.start` when explicitly registered for that phase. Provider changes are rejected at turn start. A newly created provider uses a private loopback base URL. The ordinary Core channel API remains available, including when no traffic source is requested. Registering task configuration alone does not activate transparent source coverage.

On builds that report `threadConfiguration.reconfigureLoadedThread`, `codex.backend.write@1` method `threads.reconfigure({threadId, modelProvider, model})` applies a registered resume hook to the selected, idle, locally owned task. The reviewed native manager unsubscribes and resumes the same task, preserving its history/workspace/permissions and resetting provider continuation state. A native resume receipt must confirm both expected values before `status: applied` is returned. Active turns, pending approvals and non-selected tasks are rejected; the API never automatically interrupts a conversation. Failure after release is not proof the old provider remains active: keep the associated channel alive and inspect/recover before retiring it. Windows build 10789's manager lifecycle and backend HTTP/WS reconfiguration have been reviewed; other builds remain explicitly unsupported until reviewed.

For owned automatic restoration, use Desktop Adapter 0.2.14's configuration handle with `restoreOnDeactivate: true` and `handle.reconfigure(...)` on Core 0.2.0. This records the original provider/model and verifies the applying owner and native receipt. Await `handle.restore()` before explicit channel closure; ordinary Core cleanup also awaits it. A later user provider choice is preserved, and uncertain/busy/forced cleanup reports `restoreRequired` rather than treating route closure as restoration. See [the exact lifecycle and scope](adapters.md#task-configuration-and-explicit-channels). Controlled tests exercise the production Core cleanup and adapter modules together; actual client acceptance is still separate.

## Launch and readiness

Desktop Adapter 0.2.10 exports `clientSource` through its ordinary granted `codlet.client.launch@1/runtime` Host entry. Core Preview 27 establishes a generic bridge before native entry independently of this plugin and closes the temporary inspector. The Adapter matches original captured module hashes before installing hooks on live classes, including classes initialized while the source was unavailable. Main hooks join the same enable/reload/update/rollback/disable/revoke receipt as the rest of the plugin. Failed validation preserves old hooks; failed activation permits rollback. Module subscriptions and callbacks retire, while Core-owned backend forwarding routes survive source replacement until their child exits. A first late recovery reconnects only reviewed idle local backends and rejects pending requests or active turns; it does not restart the desktop. Each Desktop/model path still reports separate bounded activation metadata.

The Adapter retains `prepareClientLaunch`, `beforeClientResume` and `attachClientLaunch` for older Core versions. Those one-shot startup exports keep their reviewed image guards and require a new client launch after a suspended startup. Preview 27 instead owns the public Electron fuse/inspector substrate; private application/backend fingerprints remain here. See [Windows startup](windows-startup-bootstrap.md).

The retired CONNECT proxy, forged launch CA, Session proxy/certificate verifier, code-mode sidecar and MCP environment wrappers are absent from production. Parent, tool and MCP process environments retain the official values. The new private provider route forwards HTTP/SSE and WS with cancellation and bounded bodies/frames; it does not disable TLS verification.

## Developer checks

`tests/electron_plaintext.test.mjs` verifies the scoped Desktop fetch and progress branches, native redirect final URL tracking, cross-origin ambient credentials and the exact-owned Stdio task rewrite. `tests/backend_spawn.test.mjs` verifies effective provider routes, owned-child selection, unchanged environment, account route update and scoped CA input. `tests/electron_bootstrap_protocol.test.mjs` exercises the real Node inspector handshake; it is not an official Desktop acceptance substitute. The opt-in owned drivers under `scripts/verify-plaintext-*.mjs` exercise controlled official binaries without modifying installed files. On Apple Silicon, `scripts/verify-plaintext-backend.mjs` requires an explicit backend hash, and `scripts/verify-official-main-owned.mjs` tests the product Host against the exact reviewed app and backend hashes. A changed build fails closed.
